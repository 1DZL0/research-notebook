## 0. Bottom line

- Against 82 checklist items drawn from the canon you named (plus four sources I added because they bear directly on coverage), Module 02 covers 30 fully, 34 partially and 18 not at all. Of the 52 gaps, 35 can be closed inside 02 with a pasted paragraph or small widget, 9 need a new section, 7 are another module's job, and 1 (OWASP edition labels) is course-wide.
- What it does, it does well, and it sits on the canonical line. OWASP's 2026 project letter ("Stop trying to build a model that cannot be fooled. Build the system around it, so that when the model is fooled, and it will be, nothing important breaks") is the module's refrain; NCSC, Microsoft's MSRC post and Anthropic's sandboxing post make the same architectural argument. The reducers it names (spotlighting, instruction hierarchy, prompt-injection classifiers such as Prompt Guard) are exactly the families that "The Attacker Moves Second" broke when the attacker adapted.
- Time-sensitive: OWASP published a 2026 edition of the LLM Top 10 (landing page dated 3 Aug 2026). Prompt Injection keeps LLM01, and its 2026 text is the closest single statement of the canon to the module's own thesis, but Excessive Agency moves from LLM06:2025 to LLM03:2026, Improper Output Handling from LLM05 to LLM10, and System Prompt Leakage becomes LLM08:2026 Hidden Context Exposure. The module and the course map still use 2025 labels.
- Missing, in order of importance (section 5): (1) the architecture family that constrains the whole run once untrusted text is in context (the Design Patterns paper: only the dual-LLM and CaMeL get a paragraph, four of the six patterns are absent); (2) honest evaluation (adaptive attackers, repeated attempts, utility cost); (3) a statement that the permission thesis does not bound what a fooled agent says, plus availability and persuasion harms; (4) technique literacy (staged, encoded, split, optimised, persuasive and user-delivered injections); (5) privilege-follows-provenance and intent checks, and the 02/03 boundary; (6) standards named by ID but not mapped, and a jailbreak definition that disagrees with the standards the page cites.
- Cheapest high-value fixes: ADD-10 (state the thesis limit), ADD-17 (adaptive attackers), ADD-13 (put the numbers behind "reducer"), ADD-19 (where this module stops), the label decision in 4.5c, and the "Plan first" exercise from LARGE-A, which needs one new profile field and one line in dispatch().

## 2. Module 02 as built

Thesis (hero, L103-166; every Part callout): the model reads one stream, so it can always be fooled; "the fix cannot live in the prompt. It lives in what the agent is allowed to do, checked outside the model" (L149-150). The organising idea is Reducer / Boundary / Detect.

Cell map (line numbers from this reading).
- Hero and "See it first" (L103-190). Four mechanisms: reads text you did not write (indirect), one stream, tools turn words into actions, memory makes it stick. An honest disclosure (L180-190) that the on-page agent is a deterministic keyword planner, not a model, "so it proves nothing about whether a model would be fooled".
- Part 1, How it breaks (L191-521). System prompt and tool view (L198-213); a definitions paragraph on indirect, direct and jailbreak (L214-231); find the attacker-controlled field, with the ForcedLeak shape (L232-261); which call persists (L262-287); the stream view and the "treat the record as data" line, with spotlighting, data marking and instruction hierarchy named as reducers (L288-319); the four faces, with the lethal trifecta in one sentence (L320-339); match the control to the action (L340-386); a keyword-filter exercise and a "beat your own filter" red exercise (L387-492); a check question (L493-514).
- Part 2, How you stop it (L522-940). Predict-then-flip switchboard of five controls (L529-624); "Why the permission, not the prompt", two columns (L625-644); a 13-model sweep guess (L645-686); three code exercises, allowed(path), allow_sql(sql, readonly) and leaks(url, loaded), with traps (L687-804); the learner's code becomes the checkpoint and four notes are fired at it (L805-874); a URL tester that probes the allowlist, SSRF, userinfo, redirects and open-redirect hosts (L875-933).

- Part 4, The surface keeps widening (L1174-1493). Eight flip-a-control cards: coding agents (1187-1226), tool output (1227-1262), invisible text (1263-1291), poisoned MCP tools (1292-1320), the rendered reply (1321-1346), the approval dialog as cover (1347-1375), browsers and computer use (1376-1408), cross-agent spread (1409-1432). A copyable 14-row checklist (L1447-1465) and a check question (L1466-1486).
- Part 5, The defender's toolbox (L1494-1602). A sort exercise, Reducer / Boundary / Detect (L1500-1535); one paragraph on lethal trifecta, Rule of Two, dual-LLM and CaMeL mapped onto Koda (L1541-1553); accordions for the layered toolbox (L1557-1568), standards and incidents (L1570-1583) and practice targets (L1585-1593).
- Part 6, Take it to your own agent (L1603-1659). A tool-inventory table, bind the top of the list, a CI test that asserts on the tool trace never the reply, benchmark your model.

Shared lab facts that bound what 02 can teach. PROFILES has two settings (lab:L23); dispatch() is the single checkpoint (lab:L80); plan() is a keyword matcher (lab:L115-141), so the page cannot express how an instruction is phrased, encoded, split or staged; the grader recognises four outcomes only, read secrets, deleted data, poisoned memory, leaked PII (lab:L557-585), all tool-call harms; the sweep data is 13 models by 2 runs for exfiltration and 6 models for the delete (lab:L203-212).

What an expert will credit. Indirect-versus-direct-versus-jailbreak is made explicit; the boundary-not-filter thesis is tested by the learner's own code; refusal reasons are withheld from the model because "a precise denial is an oracle" (L620); grading never reads the model's prose; every reducer is labelled a reducer with a reason; approval-as-cover and approval fatigue are taught; the allowlist's own bypasses (open redirect, expired domain, forwarding hosts) are taught; "baseline, bound, then CI test" is a real workflow; incidents are current and cited.

### 4.2 Small additions (paste-in)

**ADD-01. Direct injection and the jailbreak label (A3, A4).** Where: append to the markdown cell at L214-231, after the existing definitions paragraph.

> Two notes on vocabulary. The standards do not all draw the jailbreak line where this page does: OWASP's LLM01 treats a jailbreak as a subset of prompt injection, NIST AI 100-2 files both under direct prompting attacks, and Simon Willison, who coined "prompt injection", keeps the two apart. What matters for defence is not the label but whether your application's data is in the attack: a jailbreak targets the model's own rules, an injection targets your application's trust in what it reads. And direct injection is a threat in its own right, with a different shape. The attacker is the user and the victim is you: they try to make the agent act beyond their own rights, on another customer's record, through an admin tool, or to reveal your hidden instructions. The boundary is the same checkpoint, keyed to the user's identity rather than the agent's: the agent should hold no more authority than the person typing. Module 03 builds that.

**ADD-02. Why not just sanitise the input? (A5, F6).** Where: a new markdown cell directly after the stream-view cell (after L319), before the four-faces cell.

> **Why not sanitise the input, as we did for SQL?** SQL injection had a structural cure: parameterised queries keep the command and the data in separate channels, so nothing a user types can become a command. A language model has no such channel. The UK NCSC's December 2025 guidance says models "simply do not enforce a security boundary between instructions and data inside a prompt", and suggests thinking of the model as an "inherently confusable deputy": it holds your authority and can be talked into using it for someone else. OWASP's 2026 entry says the same (there is no clean equivalent to parameterised queries). That is why the fixes on this page sit outside the model, and why the NCSC expects that prompt injection "may never be totally mitigated": the aim is to cut the likelihood and, above all, the impact.

**ADD-03. The residual-risk line (A6, D15).** Where: a new step 5 in the Part 6 list (after step 4, around L1645), and one clause in the Part 6 callout (L1651).

> 5. **Write the residual-risk line.** For every row you could not bound, write the worst single call it could make, who would be hurt, and who has accepted that risk. OWASP's 2026 guidance asks for an explicit residual-risk assessment for any agent that reads untrusted input and also holds sensitive access or can change state or communicate outwards (its [A,B] and [A,C] configurations), and the UK NCSC says prompt injection may never be fully mitigated, so someone has to own what is left. If the worst call is irreversible and nothing bounds it, the honest conclusion may be that this task should not go to an agent yet. Module 09 covers the governance side.

**ADD-04. Goal hijack at agent scale (A8).** Where: the "Standards, papers" accordion (L1570-1583), directly after the ASI list.

> LLM01 describes input that alters one model response. ASI01, Agent Goal Hijack, is the same weakness at agent scale: planted text redirects the goal, the plan and every tool call after it (OWASP's agentic list gives EchoLeak and a recurring calendar invite that nudges the agent's objectives each morning as examples). This module teaches the agent case, so ASI01 is its home entry. ASI02 (tool misuse), ASI03 (identity and privilege), ASI06 (memory) and ASI09 (human trust) are the neighbours it touches; the mapping table below shows which card sits where.

**ADD-05. User-driven delivery (B3).** Where: a seventh entry in `WATCH` (lab:L308-334). Update the `assert len(WATCH) == 6` (lab:L652) and the "fourteen-row checklist" string in the Part 4 divider (L1177-1178), which counts the eight cards plus the catalogue (eighteen rows if ADD-05, ADD-06, ADD-09 and ADD-11 all go in; the comment at L1449 and the hero's "Eight more ways" at L128 count cards only and stay true).

> **Prompts the user delivers for you.**
> *How:* The attacker never reaches the agent. They put the instruction where the user will copy it from, or in a link the user will open, and the user hands it over. Greshake et al. call this a user-driven injection: the user's own session, permissions and trust do the delivery.
> *It happened:* Greshake et al. (2023) describe text copied from an attacker's page and pasted into a chatbot as a question, and "try this prompt" social engineering. Card 7's address-bar case is the browser version.
> *The bound:* Treat anything pasted or opened through a link as untrusted content, not as the user's own words: show it as quoted material, carry it as data, and require confirmation for any action that traces back to it. Provenance decides trust, not whose account the message came from.

**ADD-06. Staged injection (B5, C3).** Where: an eighth `WATCH` entry.

> **Two-stage notes.**
> *How:* The first note is short and looks harmless; its only instruction is to fetch more text from a place the attacker controls. The long, blunt second stage never sits in the record you scanned. Greshake et al. call these hidden injections, and NIST AI 100-2e2025 lists multi-stage injection under injection hiding.
> *It happened:* Greshake et al. (2023, section 4.2.4) show a compromised model fetching fresh instructions from an attacker's command-and-control server on every request, a remotely controllable backdoor.
> *The bound:* The egress allowlist stops the fetch, and anything fetched after untrusted content was read is untrusted too. Scanning the record at ingest cannot be your boundary, because the dangerous text arrives later.

**ADD-07. Five ways past a filter (B6, B7, B8, B9).** Where: a collapsed accordion, "More ways past a filter", directly after the "Beat your own filter" outcome cell (after L492).

> Rewording is one way past a filter. The standards list at least four more, and each beats a different kind of check. **Encoding and other languages:** the instruction arrives in Base64, a cipher, a low-resource language or a mix of languages, and the model is asked to decode or translate it, so a phrase list never sees the words (OWASP LLM01; MITRE ATLAS AML.T0068). **Payload splitting:** no single field holds the instruction; two harmless-looking pieces in different fields or documents only combine inside the model's context, so a per-field check passes both (OWASP's example is a CV evaluated by an LLM). **Optimised strings:** an attacker can search by machine for a run of apparently meaningless characters that pushes a model to comply; NIST AI 100-2e2025 calls the transferable ones universal adversarial triggers and describes optimised execution triggers for indirect injection, so there is no phrase for a human to list. **Persuasion:** authority, urgency, "pre-approved", or text dressed as the application's own system or role markers. The subtle note in this module is that family, and Greshake et al. found a model reached for urgency and authority by itself when it was only asked to get the user to click. A filter has to beat all of these every time. A boundary on the action does not care which one was used.

**ADD-08. Unintentional injection and the three surface tiers (B19, B17).** Where: append to the "See it first" commentary (after L190) or to the cell at L214-231.

> Two refinements. First, not every planted instruction is hostile. OWASP's LLM01 includes "unintentional injection": a job advert carries a line telling an AI to flag AI-written applications, an applicant's AI-polished CV trips it, and neither side acted maliciously. A model cannot tell a harmless note from a hostile one by reading it, so the rule is the same for both: text the agent reads can inform its answer, but only the user's request and your policy can authorise an action. Second, OWASP's 2026 edition sorts delivery surfaces by trust: untrusted (public web pages, unknown email), semi-trusted (issue titles, READMEs, third-party API responses) and trusted but reachable, such as your own CRM, which a stranger can write into through a public form or a support ticket. Koda's notes field is the third kind, and it is dangerous precisely because nobody thinks of it as an input.

**ADD-09. The answer as the weapon (C4).** Where: a ninth `WATCH` entry, with a pointer from card 6.

> **The answer talks the user into it.**
> *How:* The injection does not need a tool. It tells the assistant to recommend a link, quote a false figure or say that a payment is urgent, and the user acts because the assistant said so. No permission is touched, so nothing on this page fires.
> *It happened:* Greshake et al. (2023, section 4.2.2) steered Bing Chat to push a phishing link, and it added urgency of its own ("Hurry up, this offer is valid only for a limited time") without being told how to persuade. OWASP's agentic list names the class ASI09, human-agent trust exploitation.
> *The bound:* Outside the permission model: show where each claim came from, keep the assistant's verdict advisory for any decision that carries money or access, and make the literal action, not the assistant's description of it, the thing the human approves (card 6).

**ADD-10. The limit of the permission thesis (C5).** Where: a closing "A limit of this approach" callout at the end of the cell "Why the permission, not the prompt" (L625-644), repeated in one line in the Part 2 callout (L934).

> **A limit of this approach.** Permissions bound what a fooled agent can do; they do not bound what it can say. A poisoned page can still skew a summary, a recommendation or a screening score without a single refused call. Greshake et al. call this manipulated content, and NIST AI 100-2e2025 files it under integrity attacks. For those harms the controls are different: provenance and citations the user can open, a second independent source, the model's verdict kept advisory, and a human who decides. Every verdict on this page grades tool calls only, so a green row means "nothing bad was done", not "nothing bad was said".

**ADD-11. Burning time and money (C6, D26).** Where: a tenth `WATCH` entry; widen the rate-limit bullet at L1564 to point at it.

> **Burning time and money.**
> *How:* A planted line tells the agent to do something slow or endless: loop over a long list, call a paid tool again and again, or stop using a capability it needs. Nothing is stolen or deleted; the harm is cost and downtime, and it is cheap to cause.
> *It happened:* Greshake et al. (2023) made Bing Chat do time-consuming background work and disarm its own search tool. NIST AI 100-2e2025 lists time-consuming tasks and inhibiting capabilities as indirect-injection availability attacks (NISTAML.016, NISTAML.017); MITRE ATLAS has "agentic resource consumption" (AML.T0034.002); OWASP's agentic list calls the tool version loop amplification.
> *The bound:* Budgets for calls, spend and wall-clock time per task and per identity, enforced by the checkpoint and not by the model, with a circuit breaker that halts or escalates when one trips (OWASP Excessive Agency, rate limiting).

**ADD-12. Narrow the output as well as the input (D2).** Where: a bullet in the "Bound the impact" list of the toolbox accordion (L1557-1568), with a short pointer from card 2.

> **Narrow the output, not only the input.** If the agent only has to classify a record or choose one of five actions, make the model emit exactly that: an enum or a schema validated in ordinary code, with no free text allowed through. An injection can still skew the choice, but it has nowhere to put a command, a URL or a message. OWASP's 2026 guidance asks for the validation to be structural "rather than a second LLM call", and adds that a schema-valid answer can still carry the harm (a well-formed query against the wrong table, an email body shaped for exfiltration). This is also the idea behind the action-selector pattern in Part 5b.

**ADD-13. Spotlighting in three forms, with the evidence (D3, D4, A7).** Where: extend the stream-view cell (L298-319): replace the two-state radio with four states (plain, delimited, datamarked, encoded) rendering the same record, and use this as the caption under it.

> Spotlighting (Microsoft, 2024) has three forms. **Delimiting** wraps the untrusted text in markers the model is told to treat as data. **Datamarking** interleaves a special token between its words, so every word is visibly from outside. **Encoding** transforms it, for example into Base64, so it cannot be mistaken for the application's own voice. In its authors' GPT-family experiments it cut attack success from above 50% to below 2%, and it is worth deploying. It is still a reducer, because the model is asked to obey a convention. In "The Attacker Moves Second" (Oct 2025), spotlighting went from as low as 1% attack success against static attacks to above 95% against an adaptive one; the prompt-injection classifiers PromptGuard, Model Armor and Protect AI's detector were each beaten more than 90% of the time; and StruQ-style separated channels were bypassed in every case tested. Use these under the boundary, never in place of it.

**ADD-14. What vendors do, and what public data says (D5, E7, F7).** Where: at the end of the sweep cell (L645-686), after the "the model is not a boundary" paragraph. Flag for the author: the OpenAI sentence rests on TechCrunch's quotation of OpenAI's Atlas post (22 Dec 2025) because OpenAI's own page returned HTTP 403 to me; check the wording at source before publishing.

> Vendors are working on the model side, and it helps. Anthropic trains Claude with reinforcement learning on simulated injected web pages, scans untrusted content with classifiers and red-teams continuously; against an adaptive attacker with 100 attempts per environment its best model went from 8.0% attack success on the model alone to 1.4% with all safeguards, and the post still says "No browser agent is immune to prompt injection". Google layers model hardening, content classifiers, security reminders around the content, markdown and URL sanitisation and user confirmation. Microsoft describes the same shape (prevent, detect, limit impact) and says outright that its approach "does not rely on our ability to block all prompt injections". OpenAI trains an automated attacker with reinforcement learning to find new attacks and says prompt injection, like scams and social engineering on the web, is unlikely ever to be fully "solved". Public data agrees: in a large agent red-teaming competition (1.8 million attacks on 22 agents; Zou et al., 2025) nearly every agent violated policy within 10 to 100 queries, and robustness barely tracked model size or capability. A 1.4% rate is a good number for a vendor and a poor one for an agent that can move money; the vendors' own products add confirmations, sandboxes and allowlists for the remainder.

**ADD-15. Privilege follows provenance, and every exit is an exfiltration channel (D7, D9, D29).** Where: a new paragraph after the four-names cell (after L1553); the last two sentences go in the footer of the URL tester (L888-933).

> **A rule that sums up the page: privilege follows provenance.** An agent should act with the authority of the least-trusted party whose text is in its context. The UK NCSC puts it, after Simon Willison, as: an LLM processing information from a party should take on that party's privileges, so an assistant that reads email from strangers should not hold tools a stranger could not use. Two things you can build from it. Choose the tool set per task, so an agent that reads outside text has no write or send tool at all. And when untrusted text enters the context part-way through a session, drop the write and egress capabilities for the rest of it; product-level "lockdown" and logged-out modes are this idea applied to a whole product. The permission switches in Part 2 are the same rule applied to one tool at a time.
>
> One more thing the URL tester should say: every exit is an exfiltration channel, not only HTTP. DNS lookups, package installs, git remotes, mail and webhooks all carry data, and OWASP's agentic list records an auto-approved ping tool used to leak data over DNS.

**ADD-16. Intent checks (D12).** Where: a bullet and one paragraph in the toolbox accordion's "Bound the impact" list (L1557-1568).

> **Intent checks.** Before a call runs, compare it with what the user asked for and stop on a deviation: the lookup and the follow-up were requested, a file read and a table delete were not. OWASP's agentic guidance asks for exactly this (ASI01: validate both user intent and agent intent, and pause on an unexpected goal shift) and suggests an "intent capsule", a signed envelope that binds the declared goal and constraints to each run. Be clear what kind of control it is. If a second model judges whether the call matches, it is a reducer, because the judge reads the same poisoned text. If the plan is fixed in code before any untrusted text is read, and the checkpoint only runs calls that are in the plan, it is a boundary: that is plan-then-execute, in Part 5b.

**ADD-17. You were the adaptive attacker (E2, E3, B8).** Where: a collapsed accordion directly after the "Beat your own filter" outcome (after L492), or at the end of Part 2 before the callout (L934).

> **You just played the adaptive attacker.** You read the filter, then wrote the note it could not match. Published defences are usually tested the other way round, against a fixed set of attack strings, and that flatters them. "The Attacker Moves Second" (Nasr, Carlini and others, Oct 2025) re-ran 12 recent defences against attackers who adapt to them, using gradient search, reinforcement learning, random search and human red-teamers: most of the defences, many of which had reported near-zero attack success, were bypassed more than 90% of the time, and a public competition of over 500 people beat all 40 of its challenges. Agents behave the same way. The US CAISI and UK AISI found that stronger new attacks lifted success on AgentDojo from 11% to 81%, and that repeating each attack 25 times raised the average success rate across five injection tasks from 57% to 80%: the attacker needs one success, not a good average. So read a "blocks 99%" claim as "blocks 99% of what the vendor tried", test your own agent with the defence disclosed to the tester and with many attempts, and reject any result that is one run against a fixed string. OWASP's 2026 guidance for LLM01 says the same: reject static-only attack-success claims.

**ADD-18. What the benchmarks measure, and what a boundary costs (E4, E5, E6).** Where: a new step 3b in the Part 6 list, and a "cost" column in the inventory table (L1611-1650).

> 3b. **Measure what each boundary costs.** AgentDojo (97 tasks and 629 security cases across email, banking and travel agents) scores two things at once: whether the agent still finishes its job, and whether the attack succeeds. Copy the habit: record how many legitimate tasks still pass after each boundary you add. CaMeL, the most rigorous design in the toolbox, solved 77% of AgentDojo tasks with provable security against 84% for an undefended agent; those seven points are the price of the guarantee. InjecAgent (1,054 test cases covering direct harm and data exfiltration through tools) is a second agent benchmark, and OWASP's 2026 guidance names AgentDojo and JailbreakBench as the baselines to run before you red-team. Add a "cost" column to your table: the legitimate task this boundary breaks, and who will ask you to remove it.

## 5. Verdict

Module 02 is a strong treatment of one thing: an agent that reads text it did not write, and the argument that the fix is a permission outside the model. An expert would endorse that thesis (it is the thesis of OWASP's 2026 LLM Top 10, the NCSC, Microsoft and Anthropic's sandboxing work) and would credit the hands-on controls, the honesty about reducers and the up-to-date incidents. As a treatment of prompt injection as a whole it is a very good treatment of the action-bounding half. What is still missing, in order of importance:

1. **The architectures that constrain a whole run, not one action.** Once untrusted text is in context, the field's answer (Design Patterns paper, CaMeL, FIDES, Meta's Rule of Two) is to fix or quarantine what the agent can do for the rest of the run: action-selector, plan-then-execute, map-reduce, dual LLM, code-then-execute, context-minimisation, and narrow application-specific agents. 02 gives the dual-LLM and CaMeL one paragraph and omits four of the six patterns and the principle. This is the largest gap and the best new exercise ("Plan first" costs one profile field and one line in dispatch()). See LARGE-A.
2. **Honest evaluation.** The module's central empirical claim, "the model is not a boundary", rests on its own 13-model, two-run sweep, and its CI-test advice (Part 6 step 3) is right for the boundary but silent on method: one planted instruction proves little unless the tests also attack the checkpoint's own parsers (which Part 2 teaches) and any reducer in front of it is measured against adaptive, many-attempt attackers. The canon is unanimous: test against adaptive attackers who know the defence, with many attempts, and report the utility cost (The Attacker Moves Second; OWASP 2026 control 11; CAISI; Zou et al.; CaMeL's 77% versus 84%). The module name-drops the paper in a clause. ADD-14, ADD-17, ADD-18.
3. **The scope limit of its own thesis.** Every verdict on the page grades tool calls. Manipulated content, fraud through the assistant's answer, availability and denial of wallet, and hidden-context disclosure are real injection impacts (Greshake's six classes; NIST's availability, integrity and privacy goals) that action permissions do not bound. The module should say so (ADD-10) and teach availability and persuasion (ADD-09, ADD-11). Hidden-context disclosure is Module 05's.
4. **Technique literacy for the red hat.** The red exercises only reword text, because the planner is a keyword matcher. Staged injection, encoding and low-resource languages, payload splitting, optimised strings and Best-of-N, persuasion framing, unintentional injection and user-delivered injection are all in OWASP's scenarios or Greshake's taxonomy and none is taught (ADD-05 to ADD-08). A prose gallery is enough; no payloads are needed.
5. **Two principles between "permission per tool" and "architecture".** Privilege follows provenance (NCSC, after Willison) and intent checks against the user's original request (ASI01). Both are one paragraph (ADD-15, ADD-16). With them goes a stated 02/03 boundary against Excessive Agency (ADD-19), because 02 currently teaches most of that entry's mitigations without saying so.
6. **Vocabulary and mapping.** The jailbreak definition disagrees with the standards the page cites later (ADD-01); "not SQL injection" and the confusable deputy are only a title in a reference list (ADD-02); a residual-risk step is absent (ADD-03); the standards are named by ID but not mapped to the cards (4.5); and the OWASP labels are a year stale if the 2026 edition is the course's reference (4.5c).

What I would leave alone: the Part 1 and Part 2 arc, the learner-written checkpoint, the URL tester, the approval-as-cover card, and the reducer/boundary/detect sort. They are the module's value, and nothing in the canon contradicts them.

- Related frameworks on the page: MITRE ATLAS AML.T0051.000 (direct), AML.T0051.001 (indirect), AML.T0054 (jailbreak).

OWASP LLM06:2025 Excessive Agency (fetched genai.owasp.org/llmrisk/llm062025-excessive-agency/): root causes excessive functionality, excessive permissions, excessive autonomy. Mitigations: minimise extensions, minimise extension functionality, avoid open-ended extensions, minimise extension permissions, execute extensions in the user's context, require user approval, complete mediation (authorise in downstream systems, not via the LLM), sanitise inputs and outputs; plus logging/monitoring and rate limiting as damage limiters. OWASP Top 10 for Agentic Applications 2026 (primary PDF, "Version 2026, December 2025", read in full via pdftotext). Entries: ASI01 Agent Goal Hijack, ASI02 Tool Misuse and Exploitation, ASI03 Identity and Privilege Abuse, ASI04 Agentic Supply Chain Vulnerabilities, ASI05 Unexpected Code Execution (RCE), ASI06 Memory & Context Poisoning, ASI07 Insecure Inter-Agent Communication, ASI08 Cascading Failures, ASI09 Human-Agent Trust Exploitation, ASI10 Rogue Agents.
- ASI01 description: agents "cannot reliably distinguish instructions from related content"; goals, task selection and decision pathways can be manipulated through "prompt-based manipulation, deceptive tool outputs, malicious artefacts, forged agent-to-agent messages, or poisoned external data"; "Unlike LLM01:2025, which focuses on altering a single model response, ASI01 captures the broader agentic impact". - ASI01 mitigations (9): (1) treat all natural-language inputs as untrusted and route them through LLM01 safeguards; (2) least privilege plus human approval for high-impact or goal-changing actions; (3) define and lock system prompts, goal changes via configuration management; (4) at run time validate user intent and agent intent, require confirmation (human, policy engine or platform guardrails) when the agent deviates from the original task, block on unexpected goal shift; (5) "intent capsule" (signed envelope binding goal, constraints and context to each execution cycle); (6) sanitise and validate every connected data source (CDR, prompt-carrier detection, content filtering); (7) logging, behavioural baseline, alerts on goal drift; (8) periodic red-team tests of goal override and rollback; (9) fold agents into the insider-threat programme.

## Part B2. Vendor, architecture and evaluation notes (verified this session)

Google, "Mitigating prompt injection attacks with a layered defense strategy" (Jun 2025; blog.google/security/mitigating-prompt-injection-attacks/, redirected from security.googleblog.com). Layers: (1) model hardening / adversarial training of Gemini 2.5 ("inherent model resilience"); (2) prompt injection content classifiers trained on real-world examples; (3) security thought reinforcement (security instructions that wrap the prompt content to keep the model on the user's task); (4) markdown sanitisation and suspicious URL redaction (external image URLs not rendered, which blocks the EchoLeak exfiltration; Safe Browsing for links); (5) user confirmation framework (human-in-the-loop for risky actions such as deleting a calendar event); (6) end-user security mitigation notifications. Framing: "defense-in-depth", "elevating the difficulty, expense, and complexity faced by an attacker". Testing: manual and automated red teams, BugSWAT, the AI VRP. (The post itself does not use the phrase "adaptive attacks".)

Microsoft MSRC, "How Microsoft defends against indirect prompt injection attacks" (29 Jul 2025). Layers: prevention (hardened system prompts, Spotlighting), detection (Prompt Shields, "a probabilistic classifier-based approach", with Defender for Cloud), impact mitigation (data governance with sensitivity labels, "deterministic blocking" of exfiltration paths such as markdown-image injection, user consent / human-in-the-loop), research (FIDES, "an approach for deterministically preventing indirect prompt injection in agentic systems" via information-flow control; TaskTracker; design patterns; the LLMail-Inject challenge, 800+ participants and a 370,000-prompt dataset). Spotlighting modes: delimiting (randomised delimiters), datamarking (a token interleaved through the untrusted text), encoding (e.g. base64 or ROT13). Stated limits: "Microsoft's approach therefore does not rely on our ability to block all prompt injections"; "deterministically detecting indirect prompt injection is still an open research challenge"; the design goal is that "successful injections don't lead to security impact".

Spotlighting paper (arXiv 2403.14720, Hines et al.): reports ASR from above 50 percent to below 2 percent on GPT-family models in their experiments (abstract). Instruction Hierarchy (arXiv 2404.13208, Wallace et al., OpenAI): train models to "selectively ignore lower-privileged instructions"; the abstract claims "drastically increases robustness" on GPT-3.5 with "minimal degradations on standard capabilities".

Meta, "Agents Rule of Two" (Oct 2025; ai.meta.com/blog/practical-ai-agent-security/). [A] an agent can process untrustworthy inputs; [B] it can have access to sensitive systems or private data; [C] it can change state or communicate externally. Rule: until prompt injection can be reliably detected and refused, satisfy no more than two within a session; if all three are needed, no autonomous run, require supervision (human approval) or a fresh context window. Inspired by Chromium's rule of 2 and Willison's trifecta. Explicit non-claims: not sufficient against other threats, not a finish line (a user blindly confirming defeats it), not a substitute for defence in depth or least privilege (paraphrase), reduces severity but "does not claim to stop all attacks". Note the Meta definition of [C] ("change state OR communicate externally") is broader than the trifecta's third leg (external communication only); 02 uses the Meta wording correctly.

CaMeL (arXiv 2503.18813, Debenedetti, Shumailov, ..., Carlini, ..., Tramer; v2 24 Jun 2025): "a protective system layer around the LLM"; "explicitly extracts the control and data flows from the (trusted) query, so untrusted retrieved data can never impact the program flow"; capabilities "to prevent the exfiltration of private data" by enforcing security policies at tool calls; AgentDojo: 77 percent of tasks with provable security versus 84 percent undefended (the utility cost is part of the lesson).

"The Attacker Moves Second" (arXiv 2510.09023, Nasr, Carlini, Sitawarin, Schulhoff, Hayes, ..., Tramer; 10 Oct 2025): evaluates 12 recent defences; gradient, reinforcement-learning, random-search and human-guided attacks; attack success "above 90 percent for most defenses", which "originally reported near-zero attack success rates"; lesson: defences must be evaluated against adaptive attackers "who explicitly modify their attack strategy to counter a defense's design".

AgentDojo (arXiv 2406.13352, NeurIPS 2024 D&B track; ETH SPY Lab): 97 realistic tasks, 629 security test cases; email client, e-banking, travel booking; extensible for "new agent tasks, defenses, and adaptive attacks"; finds attacks and defences both imperfect and models failing many tasks even without attack. InjecAgent (arXiv 2403.02691, Zhan, Liang, Ying, Kang): 1,054 test cases, 17 user tools, 62 attacker tools; two attacker intentions (direct harm to users, exfiltration of private data); ReAct-prompted GPT-4 vulnerable 24 percent of the time, "nearly doubling" with a hacking prompt.

Anthropic, "Mitigating the risk of prompt injections in browser use" (24 Nov 2025; anthropic.com/research/prompt-injection-defenses). Layers: RL training on simulated injected web content; classifiers scanning all untrusted content entering context; human red teaming and external arena challenges. Numbers: ASR against an internal adaptive Best-of-N attacker (100 attempts per environment): Opus 4.5 8.0 percent model-only, 1.4 percent with improved safeguards; Sonnet 4.5 13.8 to 1.9; Haiku 4.5 12.0 to 2.4. Quote: "No browser agent is immune to prompt injection"; "prompt injection is far from a solved problem". Earlier, "Piloting Claude in Chrome" (Aug 2025; claude.com/blog/claude-for-chrome): 123 test cases over 29 scenarios, 23.6 percent ASR without mitigations falling to 11.2 percent with them; defences: site-level permissions, action confirmations, blocking high-risk site categories, classifiers.

TechCrunch (22 Dec 2025) reproduces OpenAI's Atlas post: "Prompt injection, much like scams and social engineering on the web, is unlikely to ever be fully 'solved'"; agent mode "expands the security threat surface"; an "LLM-based automated attacker" trained with reinforcement learning finds multi-step attacks that feed adversarial training and system-level safeguards; user advice: limit logged-in access, review confirmations, give specific instructions rather than wide latitude. LLM01:2026 Prompt Injection, current wording:
- Definition: input ("direct user input, retrieved content, tool output, image, audio, or video content, intermediate reasoning, or persistent memory") that "alters the model's behavior in ways the application developer did not intend". "LLMs make no architectural distinction between 'instructions' and 'data'... so there is no clean equivalent to parameterized queries (NCSC, 2025)". Three deployment properties that make it worse: context-window pooling, memory persistence, agentic execution (tool outputs re-enter context, "chained or self-replicating effects").
- Anatomy along three axes, "a useful threat-modeling step before selecting which mitigations apply": delivery surface (direct input, retrieved content, tool output, tool connection channel, persistent memory); propagation behaviour (single-shot, multi-step kill chain, cross-session through memory or RAG, self-replicating across agents); encoding (plain text, base64 or other obfuscation, invisible Unicode, multimodal or steganographic, low-resource language).
- Types: direct (intentional jailbreak or unintentional); "Jailbreaking is the subset of prompt injection where the attacker's goal is to make the model violate its safety protocols"; indirect, with trust tiers of delivery surface: untrusted (public web, unknown email), semi-trusted (issue titles, READMEs, third-party API responses), trusted-but-attacker-reachable (own repos, databases, tickets reached through a low-privilege channel such as a public form); "the user's own LLM instance" becomes "the weapon against the user's own backend".
- 8 common examples: direct override; indirect via retrieved content (EmailGPT); trusted-surface indirect (Invariant Labs GitHub MCP, General Analysis Supabase MCP, Rehberger); multimodal and steganographic; invisible-character injection and exfiltration (tag-block, variation-selector, zero-width; M365 Copilot ASCII smuggling); cross-session memory and RAG poisoning; fine-tuning interface as gradient oracle; multilingual, encoded or low-resource-language payloads.
- Prevention: "no reliable prevention mechanism exists today... Defense is therefore architectural rather than interceptive. Design the surrounding system on the explicit assumption that the model's instruction boundary will eventually be bypassed". Controls "reduce injection success and are expected to degrade against adaptive attackers. Others bound the blast radius once injection succeeds, and these are what survive". Eleven controls: (1) constrain role and capabilities in the system prompt (partial; "an attacker who infers the prompt can bypass it"); (2) strict output schema validated in trusted code, "structural validation rather than a second LLM call" (catches format, not semantic manipulation); (3) filter at every modality boundary (OCR over images, transcription over audio); (4) hold credentials and state-change capability in application code, least privilege per operation, "a deterministic policy engine that re-validates intent and arguments at execution time"; (5) strip tag-block, variation-selector and zero-width characters at every ingest and render boundary; (6) structurally separate, provenance-labelled channel, which "reduces attack success in non-adaptive tests only... StruQ was bypassed under adaptive attack"; (7) human confirmation of "the exact rendered action rather than a summary", noting invisible characters can make the displayed action differ from the executed one and approval fatigue; (8) Rule of Two as a floor: any [A,B,C] agent needs per-action human approval, [A,B] or [A,C] "need an explicit residual-risk assessment"; (9) treat memory writes as privileged operations; (10) pin, sign and verify MCP servers and tool packages, audit tool descriptions, monitor tool composition; (11) "Test against adaptive attackers who have read the deployed defense, and reject static-only attack-success claims", baseline with AgentDojo and JailbreakBench, red-team with the defence specification disclosed.
- 9 scenarios (each tagged with anatomy): direct injection; indirect via retrieved web content (markdown-image exfiltration); unintentional injection; RAG repository poisoning (five poisoned documents reached about 90% success in one study); payload splitting across resume fields; multimodal steganographic injection; zero-click document-borne agentic exfiltration (EchoLeak); agentic destructive command execution (Amazon Q, July 2025); trusted-backend indirect injection through MCP (GitHub issue, Supabase service_role, malicious postmark-mcp package).
- The 2026 edition drops "adversarial suffix" as a numbered scenario and folds encodings into example 8.

Design Patterns for Securing LLM Agents against Prompt Injections (arXiv 2506.08837 v3, read from arxiv.org/html). Principle: "once an LLM agent has ingested untrusted input, it must be constrained" so untrusted input cannot trigger consequential actions. Patterns and the paper's own limits: Action-Selector (an "LLM-modulated 'switch' statement", tool results never feed back; "pushes most of the work into the design of the predefined commands"); Plan-Then-Execute (fixed action list before untrusted data, which the paper describes as a form of control-flow integrity; "does not prevent all prompt injections", not those in the user prompt; may be hard for tasks that cannot be planned); LLM Map-Reduce (isolated agent per piece of third-party data; reduce step without an LLM or with constrained outputs); Dual LLM (privileged plus quarantined; "the quarantined LLM is still susceptible to prompt injection"); Code-Then-Execute (the LLM writes a program; parameters of actions can still be influenced); Context-Minimization (drop the user prompt from context after it informs the first action). Recommendations: prioritise application-specific agents with defined trust boundaries (the authors argue general-purpose agents are currently out of reach for strong security guarantees); use a combination of patterns; sandboxing and user confirmation as baseline. Ten case studies (OS assistant, SQL agent, email and calendar assistant, customer service chatbot, booking assistant, product recommender, resume screening, medication leaflet chatbot, medical diagnosis, software engineering agent). The abstract says it discusses "utility-security trade-offs".

"The Attacker Moves Second", defences actually evaluated (arXiv 2510.09023, read from arxiv.org/html): prompting defences Spotlighting (static ASR as low as 1%, adaptive search above 95%), Prompt Sandwiching (adaptive above 95%), RPO (RL 98%, gradient 96%); training defences StruQ (RL succeeded in every case tested), MetaSecAlign (2% on static AgentDojo, search 96%), Circuit Breakers (RL 100% on HarmBench); filtering defences Protect AI Detector, PromptGuard, Model Armor (search above 90%), PIGuard (71%); secret-knowledge defences Data Sentinel (bypassed in every case), MELON (76% rising to 95% with knowledge of the defence). Human red-teaming: over 500 participants, "collectively succeeds 100% of the time" on all 40 challenges. The paper itself warns the numbers are from different attacks and benchmarks and are not directly comparable across defences.
