### 1.1 OWASP Top 10 for LLM Applications 2025 (v2.0) : read in full (official PDF)

Primary: https://genai.owasp.org/llmrisk/llm062025-excessive-agency/ and the PDF https://owasp.org/www-project-top-10-for-large-language-model-applications/assets/PDF/OWASP-Top-10-for-LLMs-v2025.pdf

**LLM06:2025 Excessive Agency.** Definition (paraphrased from the PDF): the vulnerability that lets damaging actions happen in response to unexpected, ambiguous or manipulated LLM output, "regardless of what is causing the LLM to malfunction". Triggers named: hallucination or confabulation, and direct or indirect prompt injection (including from an earlier malicious extension or, in multi-agent systems, a compromised peer agent). The note says it differs from Improper Output Handling, which is about insufficient scrutiny of outputs.

The three sub-types (the page's "root cause" list, in this order):
1. Excessive functionality: the agent can reach functions it does not need.
2. Excessive permissions: the tool holds more rights on the downstream system than the task needs.
3. Excessive autonomy: high-impact actions are not independently verified or approved.

The six listed "Common Examples of Risks" (paraphrased; numbering is the official one):
1. Functionality: an extension meant to read documents also includes modify and delete.
2. Functionality: a trial extension dropped in development remains available to the agent.
3. Functionality: an open-ended extension fails to filter commands (the shell-command extension that does not stop other shell commands).
4. Permissions: a read tool connects to the database with an identity that has SELECT, UPDATE, INSERT and DELETE.
5. Permissions: a per-user extension uses a generic high-privilege identity that reaches every user's files.
6. Autonomy: an extension that deletes a user's documents does so with no confirmation.

The eight prevention items (official titles verbatim, then the gist):
1. Minimize extensions (do not offer a URL fetcher if the system does not need to fetch URLs).
2. Minimize extension functionality (a mailbox summariser needs read, not send or delete).
3. Avoid open-ended extensions (run a shell command, fetch a URL); build a specific file-writing tool instead.
4. Minimize extension permissions (enforce through the database identity the extension connects with, e.g. read-only on a products table).
5. Execute extensions in user's context (OAuth with the minimum scope; user authorisation tracked through to the downstream system).
6. Require user approval (human-in-the-loop for high-impact actions, implemented in the downstream system or inside the extension that does the 'post').
7. Complete mediation (authorisation in downstream systems "rather than relying on an LLM to decide"; every request via an extension validated against policy).
8. Sanitise LLM inputs and outputs (ASVS, SAST, DAST, IAST).

Damage-limiting options (explicitly "will not prevent Excessive Agency"): log and monitor extension and downstream activity; rate-limit.

Example scenario (the only one on the page): a mailbox assistant whose plugin can also send; an indirect injection in an incoming email makes it forward sensitive mail to the attacker. Fixes named: a read-only extension (functionality), a read-only OAuth scope (permissions), the user manually reviews and sends every drafted mail (autonomy); rate limiting the send interface as damage reduction.

Reference links on the page include PromptArmor on Slack AI exfiltration, Twilio "Rogue Agents", Embrace The Red on the confused deputy / cross-plugin request forgery, NVIDIA NeMo Guardrails guidelines, Simon Willison's Dual LLM pattern, and NVIDIA on sandboxing agentic workflows with WebAssembly (the last appears on the web page, not in the PDF).

**LLM05:2025 Improper Output Handling (tools as the sink).** "insufficient validation, sanitization, and handling of the outputs generated by large language models before they are passed downstream". The impacts it lists include XSS and CSRF in browsers and "SSRF, privilege escalation, or remote code execution on backend systems". Examples: output piped to a shell or eval; LLM-generated SQL without parameterisation; output used to build file paths (path traversal). Its first mitigation is the Module 03 sentence: "Treat the model as any other user, adopting a zero-trust approach, and apply proper input validation on responses coming from the model to backend functions." Also parameterised queries, context-aware encoding, CSP, logging. Its conditions that raise impact include "The application grants the LLM privileges beyond what is intended for end users" and "3rd party extensions do not adequately validate inputs".

**LLM07:2025 System Prompt Leakage (relevance to tools).** The page says the system prompt "should not be considered a secret, nor should it be used as a security control", and the real risk is "delegating these [session management and authorization checks] to the LLM". Mitigation 4 is the reduce/bound point for Module 03: "Ensure that security controls are enforced independently from the LLM": privilege separation and authorisation bounds checks "must not be delegated to the LLM... These controls need to occur in a deterministic, auditable manner". Example scenario 1 is a credential for a tool placed in the system prompt and leaked. Use in 03: credentials for tools must never sit in the prompt; this is the bridge to per-tool credentials held by the dispatcher.

Also relevant (not read in full): LLM03:2025 Supply Chain (static dependencies; ASI04 says it "focuses on static dependencies"), LLM10:2025 Unbounded Consumption (cost and loops), LLM01:2025 Prompt Injection (module 02).

### 1.2 OWASP Top 10 for Agentic Applications 2026 (ASI01 to ASI10) : read in full (official PDF)

Primary: https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/ (page says released 9 December 2025) and the PDF https://genai.owasp.org/download/52117/?tmstv=1765059207 ("Version 2026, December 2025", OWASP Gen AI Security Project, Agentic Security Initiative; CC BY-SA 4.0; chair John Sotiropoulos, lead Keren Katz, co-lead Ron F. Del Rosario).

Official names, verbatim from the PDF contents page and headings:
- ASI01: Agent Goal Hijack
- ASI02: Tool Misuse and Exploitation (the appendices print "Tool Misuse & Exploitation")
- ASI03: Identity and Privilege Abuse (appendices: "Identity & Privilege Abuse")
- ASI04: Agentic Supply Chain Vulnerabilities
- ASI05: Unexpected Code Execution (RCE)
- ASI06: Memory & Context Poisoning
- ASI07: Insecure Inter-Agent Communication
- ASI08: Cascading Failures
- ASI09: Human-Agent Trust Exploitation
- ASI10: Rogue Agents

The sentence that frames Module 03 (letter from the leaders): "We expand on the concepts of Least-Privilege and Excessive Agency by citing Least-Agency. This captures our advice to organizations to avoid unnecessary autonomy; deploying agentic behavior where it is not needed expands the attack surface without adding value." Also: "strong observability becomes non-negotiable".

Official boundary statements between entries (these decide where each topic sits; quote them in the module rather than inventing a split):
- ASI02 vs ASI03 vs ASI05 vs ASI04. ASI02 "covers cases where the agent operates within its authorized privileges but applies a legitimate tool in an unsafe or unintended way - for example deleting valuable data, over-invoking costly APIs, or exfiltrating information". "If the misuse involves privilege escalation or credential inheritance, it falls under ASI03"; if it "results in arbitrary or injected code execution, it is classified under ASI05"; and "tool definitions increasingly come via MCP servers, creating a natural overlap with ASI04".
- Tool poisoning is deliberately split. It sits under ASI02 when "the attacker manipulates the interface of an otherwise legitimate tool at runtime" (MCP descriptors, schemas, metadata, routing); "only cases where the tool itself is malicious or compromised at the source fall under ASI04". ASI04 nevertheless also lists "Tool-descriptor injection" and "MCP Tool Descriptor Poisoning" (the Invariant GitHub MCP case) among its own examples, so the split is real but leaky. Say so in the module.
- ASI02 "builds on the mitigations of LLM06:2025 (Excessive Agency) by extending them to multi-step agentic workflows"; LLM06 "focuses on model-level autonomy", ASI02 on "misuse of legitimate tools within agentic plans and delegation chains".
- ASI03 is "the agentic evolution of Excessive Agency (LLM06:2025)", maps "one-to-one to T3: Privilege Compromise", and names the attribution gap: without "a distinct, governed identity of its own, an agent operates in an attribution gap that makes enforcing true least privilege impossible". Its examples include "Cross-Agent Trust Exploitation (Confused Deputy)", "Un-scoped Privilege Inheritance", "Memory-Based Privilege Retention", time-of-check to time-of-use drift ("Workflow Authorization Drift"), "Synthetic Identity Injection" and "Identity Sharing".
- ASI04: "Supply chain is covered in depth in LLM03:2025... However, its focus is on static dependencies." Agentic ecosystems "compose capabilities at runtime", creating "a live supply chain". Maps to T17 plus T2, T11, T12, T13, T16.
- ASI05 "focuses on unexpected or adversarial execution of code... outcomes that require host and runtime-specific mitigations beyond ordinary tool-use controls" (so the sandbox half is Module 06). Builds on LLM01 and LLM05.
- ASI08 "describes the propagation and amplification of an initial fault-not the initial vulnerability itself".
- ASI09 "is about human misperception or over-reliance whereas ASI10 is agent intent deviation". ASI10 "focuses on the loss of behavioral integrity and governance once the drift begins, not the initial intrusion itself" and is distinguished from "Excessive Agency (LLM06:2025), which focuses on over-granted permissions".

Official mitigation names worth reusing (verbatim headings from the ASI PDF):
- ASI02: Least Agency and Least Privilege for Tools (per-tool profiles of scopes, maximum rate and egress allowlists, "expressed as IAM or authorization policy stanzas attached to each tool"); Action-Level Authentication and Approval (with "a pre-execution plan or dry-run diff"); Execution Sandboxes and Egress Controls; Policy Enforcement Middleware ("Intent Gate") (a PEP/PDP that "validates intent and arguments, enforces schemas and rate limits, issues short-lived credentials"); Adaptive Tool Budgeting; Just-in-Time and Ephemeral Access; Semantic and Identity Validation ("Semantic Firewalls") (fully qualified tool names and version pins, fail closed on ambiguous resolution); Logging, Monitoring, and Drift Detection.
- ASI03: Enforce Task-Scoped, Time-Bound Permissions; Isolate Agent Identities and Contexts; Mandate Per-Action Authorization; Apply Human-in-the-Loop for Privilege Escalation; Define Intent (bind OAuth tokens to a signed intent: subject, audience, purpose, session); Evaluate Agentic Identity Management Platforms (names Microsoft Entra, AWS Bedrock Agents, Salesforce Agentforce, Workday, Google Vertex AI); Bind permissions to subject, resource, purpose, and duration; Detect Delegated and Transitive Permissions.
- ASI04: Provenance and SBOMs, AIBOMs; Dependency gatekeeping ("Allowlist and pin"); Containment and builds; Pinning ("by content hash and commit ID", staged rollout, auto-rollback on hash drift); Supply chain kill switch ("emergency revocation mechanisms that can instantly disable specific tools, prompts, or agent connections across all deployments").
- ASI05: ban eval; sandboxed containers with network limits; "separate code generation from execution with validation gates"; allowlist for auto-execution under version control.
- ASI09: Explicit confirmations; "Separate preview from effect"; give a "plain-language risk summary (not model-generated rationales)"; Adaptive Trust Calibration; plan-divergence detection.
- ASI10: Containment and Response ("kill-switches and credential revocation"); Isolation and Boundaries (trust zones); signed behavioural manifests declaring expected capabilities and tools; keys never directly available to agents.

Incident tracker: Appendix D of the PDF lists dated incidents with ASI mappings (Replit July 2025, Amazon Q July 2025, postmark-mcp September 2025, Framelink Figma MCP RCE October 2025, MCP Inspector June 2025, Heroku MCP June 2025, ForcedLeak September 2025, EchoLeak, GitPublic issue repo hijack May 2025, and others). The live tracker is in the OWASP GitHub repo (path: initiatives/agent_security_initiative/ASI Agentic Exploits & Incidents/ASI_Agentic_Exploits_Incidents.md under https://github.com/OWASP/www-project-top-10-for-large-language-model-applications). I used it as a lead list, then checked primary sources for the catalogue examples (section 2).

Inconsistency inside the OWASP corpus to avoid propagating: the ASI PDF maps ASI06 to "T4 Memory Overload", "T6 Broken Goals" and "T12 Shared Memory Poisoning", but the Threats and Mitigations v1.1 document names T4 "Resource Overload", T6 "Intent Breaking & Goal Manipulation" and T12 "Agent Communication Poisoning". Use the Threats and Mitigations names (section 1.3) as authoritative.

### 1.3 OWASP "Agentic AI - Threats and Mitigations" (T1 to T17) : read in full (official PDF)

Primary: https://genai.owasp.org/resource/agentic-ai-threats-and-mitigations/ . The landing page I fetched still says "v1.0, February 17, 2025", but the PDF it links (https://genai.owasp.org/download/45674/) is headed "Version 1.1, December 2025". So T1 to T15 are the February 2025 list and T16 and T17 were added in v1.1. I could not confirm the date v1.1 first appeared (the PDF header says December 2025).

Official names (verbatim, Detailed Threat Model table): T1 Memory Poisoning; T2 Tool Misuse; T3 Privilege Compromise; T4 Resource Overload; T5 Cascading Hallucination Attacks; T6 Intent Breaking & Goal Manipulation; T7 Misaligned & Deceptive Behaviors; T8 Repudiation & Untraceability; T9 Identity Spoofing & Impersonation (the text adds "Agent Identity Compromise" and names theft of a persistent agent identity such as Microsoft Entra Agent ID); T10 Overwhelming Human in the Loop; T11 Unexpected RCE and Code Attacks; T12 Agent Communication Poisoning; T13 Rogue Agents in Multi-Agent Systems; T14 Human Attacks on Multi-Agent Systems; T15 Human Manipulation; T16 Insecure Inter-Agent Protocol Abuse (MCP and A2A, "consent bypass or context hijacking"); T17 Supply Chain Compromise.

T2 Tool Misuse is defined as abuse of integrated tools "operating within authorized permissions", and includes "Agent Hijacking" (it cites the NIST technical blog on agent hijacking). T3 is permission-management weakness, "often involves dynamic role inheritance or misconfigurations".

Mitigation structure: six playbooks, each in Proactive / Reactive / Detective steps (a near match for the course's reduce / bound / detect). Module 03 owns Playbook 3 "Securing AI Tool Execution & Preventing Unauthorized Actions Across Supply Chains" (mitigates T2, T3, T11, T4, T17) and Playbook 4 "Strengthening Authentication, Identity & Privilege Controls" (T3, T9). Playbook 3 proactive items: tool access control policies; "function-level authentication before an AI can use a tool"; sandboxes that reset after each execution; rate limiting; risk-scored execution; "just-in-time (JIT) access for AI tool usage"; signed agent cards, prompt templates and tool definitions with SBOMs. Reactive: log all tool interactions; "Detect command chaining that circumvents security policies"; "explicit user approval for AI tool executions involving financial, medical, or administrative functions"; "Detect abnormal tool execution frequency". Detective: auto-suspend processes over resource thresholds; limit "concurrent AI-initiated system modification requests".

Discrepancy to flag (could not resolve): the project page and README list MCP06 as "Prompt Injection via Contextual Payloads", but the entry file in the repository (2025/MCP06-2025-Intent-Flow-Subversion.md) carries the front-matter title "MCP06:2025 - Intent Flow Subversion". Cite both or cite the id only. Earlier drafts and third-party write-ups use "Intent Flow Subversion".

What the three entries I read say that Module 03 can reuse:
- MCP03 Tool Poisoning is written around "schema poisoning" (an attacker alters the contract that defines how agents call tools, e.g. remaps an operation named archive to DELETE) and description-text poisoning; it lists static indicators (model-directed commands, credential paths, exfiltration verbs near external destinations, hidden Unicode). It does not itself describe rug pulls or tool shadowing, though it cites Trail of Bits' description-pinning work. Controls it names: signed schemas and manifest integrity, immutable versioned registry, policy-as-code for semantic constraints (an invariant such as "archive must not map to DELETE", e.g. in OPA/Rego), schema provenance with the hash logged on each invocation, and runtime revalidation that binds the schema hash to agent identity and session.
- MCP02 Scope Creep: warning signs include shared agent accounts, tokens that never expire, "unclear which agent performed which action". Controls: least privilege by design, policy-as-code, expiry and just-in-time access, per-agent identity and credential binding, entitlement reviews, runtime action allowlists.
- MCP07: its test is whether you can say "who did what, and with what authority". Controls: mTLS or short-lived scoped tokens bound to agent identity, deny-by-default authorisation checked on every request, policy decision point, per-environment credentials. Its attack scenarios include token replay, a testing agent sharing production scope, and an assistant agent inheriting a parent's credentials through shared context.

### 1.6 Microsoft AI Red Team "Taxonomy of Failure Modes in Agentic AI Systems" (April 2025) : read in full (official PDF)

Primary PDF: https://cdn-dynmedia-1.microsoft.com/is/content/microsoftcorp/microsoft/final/en-us/microsoft-brand/documents/Taxonomy-of-Failure-Mode-in-Agentic-AI-Systems-Whitepaper.pdf (authors led by Pete Bryan and Ram Shankar Siva Kumar). The blog announcement is from 24 April 2025: https://www.microsoft.com/en-us/security/blog/2025/04/24/new-whitepaper-outlines-the-taxonomy-of-failure-modes-in-ai-agents/ (confirmed by a search result; I did not open the blog page itself).

Structure: two axes, security vs safety and novel vs existing. Failure mode names (verbatim):
- Novel security: Agent compromise; Agent injection; Agent impersonation; Agent provisioning poisoning; Agent flow manipulation; Multi-agent jailbreaks.
- Novel safety: Intra-agent RAI issues; Harms of allocation in multi-user scenarios; Organizational knowledge loss; Prioritization leading to user safety issues.
- Existing security: Memory poisoning; Targeted knowledge base poisoning; Cross domain prompt injection (XPIA); Human-in-the-loop (HitL) bypass; Tool compromise; Incorrect permissions; Resource exhaustion; Insufficient isolation; Excessive agency; Loss of data provenance.
- Existing safety: Insufficient transparency and accountability; User impersonation; Parasocial relationships; Bias amplification; Insufficient intelligibility for meaningful consent; Hallucinations; Misinterpretation of instructions.

The ones that belong to Module 03: Tool compromise ("a threat actor compromises a tool or function available to an agent to use the invocation of that plugin or response from it to manipulate the agent"); Incorrect permissions ("permission to access data or perform actions that are above and beyond those provided to an end user"); Excessive agency; Insufficient isolation; Resource exhaustion (its scenario: a prompt makes the system call a reviewer agent 100,000 times and exhausts the endpoint's token limit); HitL bypass (approval flooding until the user "becomes fatigued with the prompts and approves"); Insufficient intelligibility for meaningful consent (the approval says "send an email" but not to whom or what it contains); Misinterpretation of instructions (a user says "get rid of it" about a record and the agent deletes the table); Prioritization leading to user safety issues (an agent short of storage deletes existing entries to add new ones); Agent provisioning poisoning.

Its mitigation areas (headings): Identity; Memory hardening; Control flow control; Environment isolation; UX design; Logging and monitoring; XPIA controls. The "Control flow control" paragraph is the nearest published statement of the Module 03 principle: "safeguards that deterministically control the flow of an agentic AI system's execution, including ensuring security controls and engagement of key agents and limiting the tools and data that can be used in certain circumstances". Its Identity paragraph says each agent "should have a unique identifier" so permissions can be granular and "an audit trail of which component performed which actions" exists. It calls XPIA "potentially the most significant failure mode for agentic AI systems".

### 1.7 The MCP specification's own security text : read (current revision)

Revision check (modelcontextprotocol.io/specification/versioning): "The current protocol version is 2026-07-28". The previous revision is 2025-11-25. The 2026-07-28 changelog removes protocol-level sessions and the initialize handshake (MCP becomes stateless), adds server/discover, and deprecates Roots, Sampling, Logging and Dynamic Client Registration (the last in favour of Client ID Metadata Documents). Earlier 2025 revisions I did not re-read: 2025-03-26 (first OAuth 2.1 authorization), 2025-06-18 (MCP servers as OAuth resource servers, RFC 9728 and RFC 8707), 2025-11-25. I state those three from memory and from the changelog's references, not from reading each revision; treat as unverified in detail.

Pages read: https://modelcontextprotocol.io/specification/latest/basic/security_best_practices , .../latest/basic/authorization , .../latest/server/tools , .../latest/index , .../2026-07-28/changelog .

Security Best Practices headings (current): Confused Deputy Problem; Token Passthrough; Server-Side Request Forgery (SSRF); State Handle Hijacking (replaces "Session Hijacking" of 2025-11-25); Local MCP Server Compromise; OAuth Authorization URL Validation; stdio Transport Security in Proxy Scenarios; Mix-Up Attacks; Localhost Redirect URI Impersonation; CIMD Trust Policies; Scope Minimization.
- Confused deputy (spec's definition of its case): an MCP proxy server that uses a static client ID with a third-party authorisation server, allows dynamic client registration, and relies on a consent cookie, lets an attacker obtain an authorisation code without the user's consent. Mitigation: "MCP proxy servers MUST implement per-client consent"; the consent page must name the client, show the third-party scopes and the redirect URI.
- Token passthrough: "an anti-pattern where an MCP server accepts tokens from an MCP client without validating that the tokens were properly issued to the MCP server"; "MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server." Authorization spec: servers "MUST validate that access tokens were issued specifically for them as the intended audience"; "MCP servers MUST NOT accept or transit any other tokens."
- SSRF: a malicious server can make the client fetch internal URLs during OAuth discovery; block private, loopback and link-local (cloud metadata) ranges, enforce HTTPS, validate redirects, use an egress proxy, beware DNS rebinding TOCTOU.
- Local MCP Server Compromise: a one-click local server config "MUST implement proper consent mechanisms prior to executing commands", showing "the exact command that will be executed, without truncation"; run servers sandboxed; prefer stdio.
- Scope Minimization: avoid wildcard or omnibus scopes; start with a minimal scope set and elevate incrementally by `WWW-Authenticate` scope challenge.
Authorization spec facts: authorisation is OPTIONAL; HTTP transports SHOULD conform; stdio servers "SHOULD NOT follow this specification, and instead retrieve credentials from the environment" (so a local stdio server inherits the user's ambient credentials: a Module 03 point). Built on OAuth 2.1 (IETF draft), RFC 9728 Protected Resource Metadata (MCP servers MUST implement), RFC 8707 Resource Indicators (clients MUST send `resource`), RFC 9207 issuer identification (clients MUST validate a present `iss`), Client ID Metadata Documents (SHOULD). 
Tools page: "there SHOULD always be a human in the loop with the ability to deny tool invocations"; "clients MUST consider tool annotations to be untrusted unless they come from trusted servers"; servers MUST validate all tool inputs, implement access controls, rate limit and sanitise outputs; clients SHOULD show tool inputs to the user before calling, validate results before passing them to the model, time out and log. Tool-name uniqueness is per server, so aggregators "SHOULD implement a disambiguation strategy such as prefixing tool names with a server identifier" (the shadowing precondition). Index page: "Tools represent arbitrary code execution and must be treated with appropriate caution" and "MCP itself cannot enforce these security principles at the protocol level".

### 1.10 Google : "Google's Approach for Secure AI Agents" (2025) and SAIF : read the paper

Paper: https://research.google/pubs/an-introduction-to-googles-approach-for-secure-ai-agents/ , PDF https://storage.googleapis.com/gweb-research2023-media/pubtools/1018686.pdf (authors Santiago (Sal) Diaz, Christoph Kern, Kara Olive; dated 2025, no day given). I read the PDF text. Two agent risks: "Rogue actions" ("unintended, harmful, or policy-violating agent behaviors") and "Sensitive data disclosure". ### 1.13 Identity: agent as the user, as a service, or as itself (standards and products)

- **Classic definition, confused deputy.** Norm Hardy, "The Confused Deputy: (or why capabilities might have been invented)", ACM SIGOPS Operating Systems Review 22(4), October 1988. The original case: a compiler with permission to write its own statistics file in a system directory was handed a user-chosen output file name that was the billing file, and the compiler's own authority overwrote billing data. Hardy's lesson, as summarised at https://en.wikipedia.org/wiki/Confused_deputy_problem (which I could open; the cap-lore.com original failed a certificate check): "bundle together the designation of an object and the permission to access that object", so a requester cannot name what it lacks authority for. Agent translation: the tool holds the credential (authority) while an attacker-influenced model supplies the designation (which record, which URL, which recipient).
- **Agents applied.** Johann Rehberger (Embrace The Red), cross plugin request forgery, 28 May 2023, the reference OWASP LLM06 cites (URL as OWASP prints it): https://embracethered.com/blog/posts/2023/chatgpt-cross-plugin-request-forgery-and-prompt-injection./ . Quote: "An LLM can trick a client application to perform other actions and tasks that it is capable of". Recommendations include that plugins should not blindly trust the model's invocations and that plugins acting as the user are high stakes.
- **Impersonation vs delegation.** RFC 8693, OAuth 2.0 Token Exchange (January 2020), https://www.rfc-editor.org/rfc/rfc8693.html : "When principal A impersonates principal B, A is given all the rights that B has"; with delegation "principal A still has its own identity separate from B"; the `act` claim "provides a means within a JWT to express that delegation has occurred". This is the precise vocabulary for "agent acting as the user" (impersonation) against "agent acting on behalf of the user" (delegation, with an actor).
- **Microsoft Entra Agent ID** (generally available; docs updated 2026): https://learn.microsoft.com/en-us/entra/agent-id/agent-identities and https://learn.microsoft.com/en-us/entra/agent-id/whats-new-agent-id . An agent identity is "a special service principal" with no credentials of its own (its blueprint holds them). Two patterns: autonomous (app tokens) and on-behalf-of ("The subject of the token is a user, while the actor is the agent identity"). Each identity can have a sponsor, "the human user or group that's accountable for an agent". Conditional Access templates exist for autonomous agents, on-behalf-of agents and blocking high-risk agents. First announced at Build in May 2025 (secondary sources; the pages I read do not give the GA date).
- **Auth0 for AI Agents** (GA announcement 19 November 2025): https://auth0.com/blog/auth0-for-ai-agents-generally-available/ . Token Vault keeps OAuth tokens out of the agent's logic; Asynchronous Authorization (CIBA) means "The agent receives a token only after the user approves the specific action", with the prompt showing "the details of what is being authorized" (paraphrase of the page). I did not verify Okta's Cross App Access in primary sources.
- **IETF.** "AI Agent Authentication and Authorization" (draft-klrc-aiagent-auth-03, 6 July 2026; authors Pieter Kasselman, Jeff Lombardo, Yaroslav Rosomakho, Brian Campbell, Nick Steele, Aaron Parecki) is shown as expired and replaced by draft-ietf-wimse-aims, "AI Identity Management System": https://datatracker.ietf.org/doc/draft-klrc-aiagent-auth/ . It builds on the WIMSE architecture and the OAuth 2.0 family. SPIFFE/SPIRE appear in secondary sources as a candidate agent workload identity; I did not verify that in a primary document.
- **OpenID Foundation**, "Identity Management for Agentic AI", 7 October 2025 (also arXiv 2510.25819): https://openid.net/new-whitepaper-tackles-ai-agent-identity-challenges/ . Announcement read via search snippet only; I did not read the full text.
- **NIST** NCCoE draft concept paper on software and AI agent identity and authorisation, February 2026: see 1.9.

### 1.14 Research vocabulary (primary sources read)

- **Tool poisoning, rug pull, shadowing.** Invariant Labs, "MCP Security Notification: Tool Poisoning Attacks", 1 April 2025, https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks . Malicious instructions in tool descriptions, which the model reads in full while "users typically only see simplified versions in their UI". Rug pull: a server changes a tool's description after approval. Shadowing: a tool description alters how the agent uses a different, trusted tool. Mitigations named: pin and hash descriptions, cross-server isolation, show model-visible text to the user, guardrails. WhatsApp follow-up, 7 April 2025 (updated 9 April), https://invariantlabs.ai/blog/whatsapp-mcp-exploited : the shadowing demonstration. It says sandboxing the malicious server "is not a relevant mitigation", because the attack works through the agent's instruction following. So the bound has to sit on the sensitive tool's arguments (the recipient), not on the poisoned server's runtime.
- **Toxic agent flow.** Invariant Labs, "GitHub MCP Exploited: Accessing private repositories via MCP", 26 May 2025, https://invariantlabs.ai/blog/mcp-github-vulnerability . "An agent is manipulated into performing unintended actions, such as leaking data or executing malicious code"; the flaw is in "the agent system's architecture, not the GitHub MCP server code"; many users pick "Always Allow", so per-call confirmation did not help. Recommended: restrict the agent to the repositories it needs (one repository per session) and monitor.
- **Argument injection and allowlisted-command bypass.** Trail of Bits (Will Vandevanter), "Prompt injection to RCE in AI agents", 22 October 2025, https://blog.trailofbits.com/2025/10/22/prompt-injection-to-rce-in-ai-agents/ . Three production agents, each exploited in one shot. Safe-command allowlists let flags of approved tools (a test runner's exec option, a git output option, a ripgrep preprocessor) run attacker programs or write files. Key sentence: "Maintaining allowlists of 'safe' commands without a sandbox is fundamentally flawed." Sandboxing is the primary control; per-tool facades with validation are "significantly better" than command lists; use `--` separators and no shell. Same family as CVEs (CVE.org records read): mcp-server-git CVE-2025-68144 (CWE-88: user-controlled arguments passed to git, flag-like values such as an output option interpreted as options), Claude Code CVE-2025-54795 (a command parsing error bypasses the confirmation prompt) and CVE-2025-55284 ("an overly broad allowlist of safe commands", file contents sent over the network without confirmation).

- **Measured prevalence of tool poisoning.** MCPTox, arXiv 2508.14925 (submitted 19 August 2025): 45 live MCP servers, 353 tools, 20 agents, 1,348 malicious test cases; highest attack success 72.8% (o1-mini); highest refusal rate under 3% (Claude-3.7-Sonnet). The authors conclude that alignment is "ineffective against malicious actions that use legitimate tools for unauthorized operation".

### Family A. Over-grant: the tool carries more authority than the task needs

#### 1. Excessive functionality (the tool surface is bigger than the task)
- **Mechanism.** The agent is offered tools, or tool functions, the task never needs: a read tool that also writes, an open-ended "run SQL" or "run a shell command" where a typed lookup would do, a trial tool nobody removed, or an internal helper accidentally registered as callable. Anything an attacker-influenced model can name, it can call.
- **Standards.** LLM06:2025 (excessive functionality, examples 1 to 3); ASI02 (over-privileged tool access); T2 Tool Misuse; Microsoft "Excessive agency"; MCP02 (partly); ATLAS AML.T0053 AI Agent Tool Invocation with mitigation AML.M0028 AI Agent Tools Permissions Configuration; NIST NISTAML.039 (effect only).
- **Documented example.** Semantic Kernel .NET SDK: a file-download helper in `SessionsPythonPlugin` was exposed as an AI-callable tool, giving arbitrary file write on the host (CVE-2026-25592, CVSS 10.0, published 2026-02-06; fixed in 1.71.0). Microsoft Defender Security Research Team, 7 May 2026: https://www.microsoft.com/en-us/security/blog/2026/05/07/prompts-become-shells-rce-vulnerabilities-ai-agent-frameworks/
- **Matched control.** A per-task tool allowlist (deny by default), narrow typed tools instead of open-ended ones, removal of leftover tools, and an explicit "exposed to the model" flag per function. OpenAI's four-factor tool rating (read-only vs write, reversibility, account permissions, financial impact) is a usable schema for the register.
- **Reduce / bound / detect.** Bound, and the cheapest bound: a tool that is not offered cannot be called, whatever the wording of the injection.
- **Koda demo.** Already in `koda_toolbox.py`: scenario `dump` (the `run_sql` tool the reply task never needed; held at the `toolbox` layer). Add: a leftover `trial_export` tool in the manifest (LLM06 example 2) and a "registered by accident" helper, so the learner audits the manifest, not the prompt. In the five-tool mock, contrast `query_db(sql)` with a typed `get_invoice(id)`.

#### 2. Excessive permissions (the credential behind the tool is broader than the task)
- **Mechanism.** The tool is right-sized but the identity it connects with is not: an admin key, a service-role key that bypasses row-level security, or one shared identity for all users. The model never needs to "escalate"; the tool already holds the authority.
- **Standards.** LLM06:2025 (excessive permissions, examples 4 and 5); ASI03 Identity and Privilege Abuse (the "agentic evolution of Excessive Agency") and ASI02 ("over-scoped tool access"); T3 Privilege Compromise; MCP02 Privilege Escalation via Scope Creep; MCP07; Microsoft "Incorrect permissions"; ATLAS AML.M0026, AML.M0027, AML.M0028; OWASP NHI5 Overprivileged NHI.
- **Documented example.** Supabase MCP with the `service_role` key, which "bypasses all row-level security": a support ticket carrying instructions could make the agent read an `integration_tokens` table and write it back where the attacker could read it. General Analysis, reported by Simon Willison, 6 July 2025: https://simonwillison.net/2025/Jul/6/supabase-mcp-lethal-trifecta/ (I read Willison's post, not General Analysis' own). Also AWS-2025-015 (23 July 2025): the Amazon Q Developer extension compromise came from "an inappropriately scoped GitHub token in their CodeBuild configuration": https://aws.amazon.com/security/security-bulletins/AWS-2025-015/
- **Matched control.** A per-tool scoped credential: a database role with SELECT on the views the task uses, a key that respects row-level security, minted per task and per user, short-lived. Complete mediation downstream (LLM06 item 7), never "the prompt says read only".
- **Reduce / bound / detect.** Bound. Module 02's own sentence applies: "A parser is a reducer, the credential is the boundary."
- **Koda demo.** Already in `koda_toolbox.py`: `SERVICE_CREDENTIAL` carries every scope with no tenant; `reference_mint(task, user)` mints `accounts:read` plus `mail:send` bound to the user's tenant; the `scope` layer refuses the rest. In the five-tool mock this is the `db_readonly` switch. Add an `exp` and an `aud` field to the credential card so classes 3 and 7 share the same widget.

#### 3. Over-scoped and long-lived OAuth tokens (delegated credentials held by integrations)
- **Mechanism.** A connector or agent integration is granted broad OAuth scopes up front and a refresh token that never expires. Whoever obtains the token (a leaked log, a breached vendor, a prompt-injected agent that can read its own configuration) inherits everything the grant allowed, for as long as it lives. The MCP spec's "Scope Minimization" section describes the preconditions: a server that publishes every scope in `scopes_supported` and a client that requests them all.
- **Standards.** MCP01 Token Mismanagement & Secret Exposure; MCP02; MCP07; ASI03 ("Enforce Task-Scoped, Time-Bound Permissions", "Define Intent"); T3; OWASP NHI7 Long-Lived Secrets; ATLAS AML.T0098 AI Agent Tool Credential Harvesting and AML.T0083 Credentials from AI Agent Configuration; MCP spec Security Best Practices "Scope Minimization"; RFC 8707 Resource Indicators.
- **Documented example.** Salesloft Drift (UNC6395, 8 to 18 August 2025): the actor used stolen OAuth tokens of the Drift third-party app to export data from many Salesforce instances and then searched it for secrets (AWS keys, passwords, Snowflake tokens). GTIG: "This issue does not stem from a vulnerability within the core Salesforce platform." Google Cloud, 27 August 2025: https://cloud.google.com/blog/topics/threat-intelligence/data-theft-salesforce-instances-via-salesloft-drift (This is a third-party integration breach, not an agent injection; it is the best documented case of what an over-broad, long-lived delegated token costs.)
- **Matched control.** Minimal initial scopes with incremental step-up; short token lifetimes; audience-bound tokens (`resource` parameter, RFC 8707); refresh tokens kept confidential; tokens held in a vault outside the agent's context (Auth0 Token Vault pattern); one-click revocation; alert on use from an unexpected origin.
- **Reduce / bound / detect.** Bound (scope, lifetime, audience) with a detect leg (use from a new origin).
- **Koda demo.** Not in `koda_toolbox.py`. Add `exp` and `aud` to the minted credential and a replay scenario: the same token presented after the task ended, or to a different tool, is refused at a new `token` layer. Show the "blast radius" number: how many tools does this token open?

#### 4. Excessive autonomy (an irreversible action with no independent check)
- **Mechanism.** The agent can do something it cannot undo (delete, pay, send externally, push to production) and no control outside the model stands in front of it. The trigger can be injection, but also plain misreading: Microsoft's taxonomy has a user saying "get rid of it" about a record and the agent dropping the table.
- **Standards.** LLM06:2025 (excessive autonomy, example 6; mitigation 6 "Require user approval"); ASI02 ("Action-Level Authentication and Approval"); T7 Misaligned & Deceptive Behaviors (partly); Microsoft "Excessive agency", "Misinterpretation of instructions", "Prioritization leading to user safety issues"; ATLAS AML.T0101 Data Destruction via AI Agent Tool Invocation, AML.M0029 Human In-the-Loop for AI Agent Actions.
- **Documented example.** Replit and SaaStr, July 2025: the founder reported that the agent deleted a production database despite an instruction not to change code, and wrote "There is no way to enforce a code freeze in vibe coding apps like Replit." The Register, 21 July 2025: https://www.theregister.com/2025/07/21/replit_saastr_vibe_coding_incident/ (single-source account from the affected customer; the article reports no vendor fixes). OWASP ASI tracker lists it as ASI01, ASI09 and ASI10.
- **Matched control.** Approval of the literal action for irreversible calls (shown by trusted code, class 21); reversible-by-design operations (soft delete, snapshots, staging); production credentials not available to the agent at all; a freeze that is a dispatcher policy, not a sentence in the prompt; dry-run diff before approval (ASI02).
- **Reduce / bound / detect.** Bound.
- **Koda demo.** Already in `koda_toolbox.py`: scenario `delete` (held at `toolbox`, or at `approval` when the tool stays). Add a `change_freeze` flag in `dispatch()` against a prompt that says "do not change anything": same note, same model call, only the policy differs. This is the cleanest way to show "instruction versus enforcement".

#### 5. Unbounded consumption and tool-call loops (budget, rate, kill switch)
- **Mechanism.** An injected or confused agent calls tools repeatedly: costly APIs, mail sends, retries, delegation to other agents. The harm is cost, outage or flood, and it scales with how fast the loop runs and how long nobody looks.
- **Standards.** LLM10:2025 Unbounded Consumption; ASI02 ("Loop amplification", "Adaptive Tool Budgeting"); ASI08 Cascading Failures; T4 Resource Overload; Microsoft "Resource exhaustion"; ATLAS AML.T0034.002 Agentic Resource Consumption and AML.M0036 Limit AI Workload Resource Consumption.
- **Documented example.** OpenAI technical report on the Hugging Face incident: "Sustained high-volume agent activity within Artifactory continued and, as a result, caused the instance to become unavailable late on July 4" (2026); on 27 June a monitor alerted and on-call advised that stopping the run "was not required". Report PDF: https://cdn.openai.com/pdf/67869394-cb91-4c12-888c-5cbd85c7814c/OpenAI-Hugging-Face%20Incident-Technical-Report.pdf . I looked for a clean public postmortem of a runaway-cost incident and found only forum and blog anecdotes (for example a claimed 11-day retry loop and a $10,811 Cloudflare bill); I am not citing figures from those because I could not verify them.
- **Matched control.** Per-session and per-identity call budgets; per-tool rate limits; a circuit breaker on repeated refusals; provider-side hard spend caps (an alert is not a cap); a kill switch that revokes the credential; the ATLAS list of limits (iterations, retries, tool calls, delegation depth, spend).
- **Reduce / bound / detect.** Bound for the caps; detect and respond for the kill switch.
- **Koda demo.** Already in `koda_toolbox.py`: scenario `runaway` (twelve sends, `FLOOD_AFTER = 3`, held at `approval`). Add a visible budget meter and a `kill_switch` state that makes every call return "revoked", so the learner sees the difference between slowing a loop and stopping it.

### Family B. Authority misdirected: the deputy spends authority on someone else's behalf

#### 6. Confused deputy (the agent spends the user's authority on an attacker's instruction)
- **Mechanism.** The agent legitimately holds the requesting user's authority (their token, their session, their tenant). Content the user did not write steers it to name an object or action the user would never have asked for, and the downstream system accepts it because the credential is valid. Hardy's 1988 compiler is the template: the authority came from the deputy, the designation (which file) came from the requester.
- **Standards.** LLM06:2025 (its reference list cites the confused-deputy post; mitigation 5 "Execute extensions in user's context"); ASI03 ("Cross-Agent Trust Exploitation (Confused Deputy)", "Identity Sharing"); ASI01; T3 and T9; MCP07; ATLAS AML.T0053 ("tools that are not directly accessible by users. Adversaries may abuse this"); NIST NISTAML.039 Compromising connected resources (effect); Microsoft "Incorrect permissions".
- **Documented example.** ServiceNow Now Assist second-order prompt injection, AppOmni, 19 November 2025: "Now Assist agents run with the privilege of the user who started the interaction", so text written by a low-privileged user in a record field can make a higher-privileged user's session recruit a more capable agent; agents were discoverable and team-grouped by default. https://appomni.com/ao-labs/ai-agent-to-agent-discovery-prompt-injection/ . Origin story: Embrace The Red, cross plugin request forgery, 28 May 2023 (URL in section 1.13).
- **Matched control.** Authorise the object, not just the tool: the tool re-checks the requested object against the calling principal's claim (tenant, user, task) and fails closed on a missing claim; bind designation to authority (hand the tool an opaque handle already scoped to the ticket's account instead of a free id); downstream per-call authorisation; segment agents by team so a low-risk agent cannot reach a privileged one; supervised mode for privileged tools.
- **Reduce / bound / detect.** Bound.
- **Koda demo.** Already in `koda_toolbox.py`: scenario `deputy` (a note says "also pull account 201", a Pafos Foods record, while Alice acts for Larnaca Marine). The scope layer cannot stop it because `accounts:read` is legitimate; the `object check` layer does. Add the capability variant (the tool takes a handle, not an id) to show Hardy's fix in a few lines.

#### 7. Token passthrough and proxy consent confusion (the MCP authorisation layer)
- **Mechanism.** An MCP server accepts a token not issued to it and forwards it downstream, or an MCP proxy fronting a third-party API with a static client id lets an attacker's dynamically registered client ride the user's earlier consent cookie. The result is a valid token in the wrong hands, issued without fresh consent, and logs that blame the wrong party.
- **Standards.** MCP spec Security Best Practices "Confused Deputy Problem" and "Token Passthrough"; authorisation spec ("MCP servers MUST NOT accept or transit any other tokens"); MCP07; MCP01; ASI03; T3, T9; RFC 8707 and RFC 9207 (mix-up).
- **Documented example.** I found no public in-the-wild incident that matches the spec's exact preconditions. The spec is the documented source (current revision 2026-07-28): https://modelcontextprotocol.io/specification/latest/basic/security_best_practices . Nearest real case, secondary sources only: CoPhish (Datadog Security Labs, October 2025), attacker-built Copilot Studio agents on a Microsoft-hosted demo page with a login button wired to a malicious OAuth app (reported by BleepingComputer; I did not open Datadog's post).
- **Matched control.** Per-client consent stored server-side and checked before the third-party flow; exact redirect-URI match; audience validation of every inbound token; never forward the client's token (use a token exchange with an actor); `iss` validation against the recorded issuer.
- **Reduce / bound / detect.** Bound (protocol level).
- **Koda demo.** Not in `koda_toolbox.py`. A small "token card" with `aud`: the mock gateway receives a token whose `aud` is the CRM, not the gateway, and must refuse it; a second card shows the passthrough variant forwarding it and the CRM logging the wrong subject.

#### 8. Toxic agent flow (the tool set itself completes the trifecta)
- **Mechanism.** No single tool is dangerous; the combination is. One tool reads untrusted text (a public issue, an inbound email, a support ticket), another reads private data, a third can write or send outwards. One injection then walks data across the gap. Module 02 owns the trifecta and the Rule of Two; Module 03 owns auditing the tool set against them.
- **Standards.** ASI02 (its scenario of chaining "a secure, internal-only CRM tool with an external email tool"); ASI01; T2; Microsoft "Cross domain prompt injection (XPIA)"; NIST NISTAML.039; ATLAS AML.T0086 Exfiltration via AI Agent Tool Invocation, AML.M0030 Restrict AI Agent Tool Invocation on Untrusted Data.
- **Documented example.** GitHub MCP "toxic agent flow", Invariant Labs, 26 May 2025: an issue in a public repository made an agent with access to private repositories leak private data into a public pull request; users on "Always Allow" did not see it. https://invariantlabs.ai/blog/mcp-github-vulnerability . A 2026 case: Microsoft's finding on the Claude Code GitHub Action (5 June 2026), where untrusted issue and pull-request content reached an agent holding workflow secrets and a file-read tool; Anthropic fixed it in Claude Code 2.1.128 on 5 May 2026 and Microsoft advises the Rule of Two. https://www.microsoft.com/en-us/security/blog/2026/06/05/securing-ci-cd-in-agentic-world-claude-code-github-action-case/
- **Matched control.** Tool-set audit (count the three legs per session); session scoping (one repository or one tenant per session); once untrusted data is in context, drop write and egress tools or require approval (ATLAS M0030; Google's example of no external email after reading a suspicious source); egress allowlist; split the agent so no session holds all three.
- **Reduce / bound / detect.** Bound.
- **Koda demo.** Module 02's mock already has the egress allowlist and the taint check. For 03 add a "tool-set audit" panel: mark each toolbox entry A (reads untrusted), B (reads sensitive), C (writes or sends); the dispatcher refuses any C call after an A read in the same session unless approved. `koda_toolbox.py` already tags `lookup_account` results as `untrusted`.

#### 9. Tenant crossing in shared tool servers
- **Mechanism.** A multi-tenant tool server or connector returns another tenant's data because tenancy is derived from request arguments, caches or a handle rather than from the verified token. The agent need not be attacked; the shared component leaks.
- **Standards.** MCP10:2025 Context Injection & Over-Sharing; MCP spec "State Handle Hijacking" (2026-07-28; "Session Hijacking" in 2025-11-25); ASI06 (its "Cross-tenant vector bleed"); Microsoft "Loss of data provenance"; LLM02:2025.
- **Documented example.** Asana's MCP server: Asana found a bug on 4 June 2025 that "could have potentially exposed certain information from your Asana domain to other Asana MCP users", took the server offline from 5 to 17 June, and required manual reconnection. The Register, 18 June 2025: https://www.theregister.com/2025/06/18/asana_mcp_server_bug/ (no customer count in that source; I am not repeating figures from other write-ups).
- **Matched control.** Derive tenant and user from the verified token, never from arguments; key stored state by `<user_id>:<handle>` with the user taken from the token (the spec's wording); per-tenant credentials; no cross-tenant caches; two-tenant tests in CI.
- **Reduce / bound / detect.** Bound, with the CI test as the detect leg.
- **Koda demo.** The two-tenant company is already in `koda_toolbox.py`. Add a memoising `lookup_account` cache keyed by id only: Bob's call returns Alice's cached record. The fix is a one-line change of the cache key to include the credential's tenant.

### Family C. Tool integrity: the tool, its description or its output is attacker-influenced

#### 10. Tool description poisoning
- **Mechanism.** Instructions hidden in a tool's name, description or parameter descriptions are read by the model in full while the user sees a short label. The tool need not even be called for the text to steer the model.
- **Standards.** MCP03:2025 Tool Poisoning; ASI02 (tool poisoning of "the interface of an otherwise legitimate tool at runtime") and ASI04 ("Tool-descriptor injection"); T2, T16, T17; Microsoft "Tool compromise"; ATLAS AML.T0110 AI Agent Tool Poisoning (.000 Definition and Instructions) and AML.T0011.002 Poisoned AI Agent Tool; NIST NISTAML.015 (effect). MCP spec: tool annotations "untrusted unless they come from trusted servers".
- **Documented example.** Invariant Labs, "MCP Security Notification: Tool Poisoning Attacks", 1 April 2025: https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks . Measured: MCPTox (arXiv 2508.14925), 45 live servers and 353 tools, 20 agents, highest attack success 72.8%, highest refusal under 3%.
- **Matched control.** Treat all tool metadata as untrusted input; review and pin by hash; show the user the full model-visible text; server allowlist; and an action-level bound (a recipient or destination allowlist), because a phrase scanner is a reducer that a reworded description walks past.
- **Reduce / bound / detect.** Reduce (scanner, pin, review) plus Bound (the action allowlist). Both halves matter; say which is which.
- **Koda demo.** Already in `koda_toolbox.py`: `TOOL_VARIANTS` (`day-one`, `reworded`, `rug-pull`) with `pin`, `scan` and `allowlist` switches. The self-check shows the pin catches only the rug pull, the scanner only the loud wording, and the allowlist all three.

#### 11. Tool shadowing and cross-server injection
- **Mechanism.** A description on server A changes how the agent uses server B's trusted tool (for example which recipient `send_message` gets), so the attacker's server never has to be called and the sensitive call is made by the trusted tool with the user's authority.
- **Standards.** MCP03 (partly); ASI02 and ASI07 (its "Agent-in-the-Middle via MCP descriptor poisoning"); T16 Insecure Inter-Agent Protocol Abuse; ATLAS AML.T0110; the MCP tools page notes that tool-name uniqueness is per server and aggregators "SHOULD implement a disambiguation strategy such as prefixing".
- **Documented example.** Invariant Labs WhatsApp MCP, 7 April 2025 (updated 9 April): a second server's description redirected the trusted WhatsApp server's send tool and exfiltrated chat history; the approval dialog hid the recipient and the body. https://invariantlabs.ai/blog/whatsapp-mcp-exploited . Invariant notes sandboxing the malicious server "is not a relevant mitigation".
- **Matched control.** Namespace tools by server; forbid one server's descriptions from naming another server's tools; one context per server where feasible; an argument-level allowlist on the sensitive tool (recipient domain or contact list); a dialog that shows the literal recipient and the whole body.
- **Reduce / bound / detect.** Bound at the sensitive tool's arguments; namespacing is a reducer.
- **Koda demo.** The existing weather tool whose description steers `send_email` is already a shadowing demonstration in effect. Make it explicit with two servers in the manifest and show that putting the weather server in a sandbox changes nothing while the recipient allowlist stops the leak.

#### 12. Rug pull (the tool changes after approval)
- **Mechanism.** The user or admin approves a tool, server or configuration once. Later the definition, the server version or the launch command changes and nothing asks again, because the approval was bound to a name rather than to content.
- **Standards.** MCP03 and MCP04; ASI04 ("Pinning", "auto-rollback on hash drift"); T17; ATLAS AML.T0109 AI Supply Chain Rug Pull [Realized] and AML.T0110.001 Implementation; Microsoft "Tool compromise"; AML.M0014 Verify AI Artifacts.
- **Documented example.** Cursor "MCPoison", CVE-2025-54136: approval of an MCP entry was "bound only to the name", so a later change to its command or arguments ran without a new prompt, including on each project reopen. Check Point Research, 5 August 2025 (disclosed 16 July; Cursor 1.3 on 29 July 2025 requires re-approval on any change, "including something as small as adding a space"): https://research.checkpoint.com/2025/cursor-vulnerability-mcpoison/ . Invariant's WhatsApp demo is the same pattern for descriptions.
- **Matched control.** Approval bound to a hash of the full definition (description, schemas, annotations) and the server version; any change blocks the tool until re-approved; staged rollout and rollback on hash drift; for remote servers, diff on every list-changed event. Trail of Bits' `mcp-context-protector` (28 July 2025) is a working trust-on-first-use implementation, with the caveat of alert fatigue.
- **Reduce / bound / detect.** Bound for this class (it removes the silent-change step); only a reducer against day-one poisoning.
- **Koda demo.** Already in `koda_toolbox.py`: variant `rug-pull` with the `pin` switch (`tool_hash`). Add a "lockfile" panel showing the approved hash beside the served hash.

#### 13. Malicious or look-alike tool, server or skill (agent supply chain)
- **Mechanism.** Tools, MCP servers, skills and plugins are dependencies that run with the agent's authority. A typosquat, a hijacked maintainer account, a poisoned update or an unvetted marketplace entry delivers hostile behaviour that no prompt can prevent, because the hostile part is the tool.
- **Standards.** MCP04 Software Supply Chain Attacks & Dependency Tampering; MCP09 Shadow MCP Servers; ASI04 Agentic Supply Chain Vulnerabilities (and its "Supply chain kill switch"); LLM03:2025; T17 Supply Chain Compromise; ATLAS AML.T0010.005 AI Agent Tool, AML.T0115.002 Publish Poisoned AI Artifacts: AI Agent Tools, AML.T0011.002; AML.M0023 AI Bill of Materials.
- **Documented example.** `postmark-mcp` on npm: version 1.0.16 (17 September 2025) added a line that blind-copied every sent email to an attacker address; reported by Koi Security as the first malicious MCP server seen in the wild and downloaded more than 1,600 times before removal (figures from search-result summaries of The Hacker News and CSO; Koi's own post redirected when I fetched it): https://thehackernews.com/2025/09/first-malicious-mcp-server-found.html ; ATLAS AML.CS0053. Also: Amazon Q Developer extension 1.84.0 (CVE-2025-8217; AWS-2025-015, 23 July 2025: https://aws.amazon.com/security/security-bulletins/AWS-2025-015/ ), where hostile code reached a release through an over-scoped CI token; and 341 malicious skills among 2,857 audited on ClawHub (Koi Security, reported 3 February 2026; fake "prerequisite" install steps): https://esecurityplanet.com/threats/hundreds-of-malicious-skills-found-in-openclaws-clawhub
- **Matched control.** Curated registry or allowlist; pin by version and hash with provenance; AIBOM; read-only review before first use; run each tool server under its own minimal credential; an action-level allowlist (the BCC would have been refused by a recipient allowlist); a supply-chain kill switch that disables a tool across all deployments; least-privilege CI tokens.
- **Reduce / bound / detect.** Reduce (vetting, pinning), Bound (credential and action allowlists), Detect (egress and recipient monitoring); the kill switch is the respond leg.
- **Koda demo.** A "tool store" card with a look-alike pair (`postmark-mcp` and `postmark-mcp-server`). The hardened profile loads only name-plus-hash entries from a lockfile; show a malicious tool that is on the lockfile and is still stopped by the recipient allowlist, which is the lesson that vetting is a reducer.

#### 14. Injection through tool results (the tool as carrier)
- **Mechanism.** The tool returns text an outsider wrote (an issue, a ticket, a web page, a search hit), and the model treats it as instruction. This is the delivery path of indirect injection. Module 02 owns the mechanism and the reduce layer; Module 03 owns the tool-side consequences: result schemas, labelling results as untrusted, and restricting what may be called after an untrusted result.
- **Standards.** MCP06:2025 (listed as "Prompt Injection via Contextual Payloads"; the entry file is titled "Intent Flow Subversion"); LLM01:2025; ASI01 Agent Goal Hijack; T6; Microsoft XPIA; NIST NISTAML.015; ATLAS AML.T0051.001 (Indirect), AML.T0099 AI Agent Tool Data Poisoning, AML.M0030.
- **Documented example.** "Living off AI": prompt injection through a Jira Service Management ticket reaching an agent using the Atlassian MCP server, Cato CTRL, 19 June 2025 (ATLAS AML.CS0039; link and date taken from the ATLAS data file; I did not open Cato's post): https://www.catonetworks.com/blog/cato-ctrl-poc-attack-targeting-atlassians-mcp/ . Also ATLAS AML.CS0045 (Backslash Security, 24 June 2025), a scraper MCP tool returning an injected page to Cursor.
- **Matched control.** Structured outputs with `outputSchema` validated by the client; results tagged with their origin; after an untrusted result, state-changing and egress tools need approval or are withdrawn (ATLAS M0030); strip active content at ingest (02's reduce layer).
- **Reduce / bound / detect.** Reduce (schemas, sanitising) and Bound (restrict tool invocation on untrusted data).
- **Koda demo.** Already modelled: `koda_toolbox.py` marks `lookup_account` results `untrusted`, and 02's taint check exists. Show the same note arriving through a tool result versus the user turn, so the learner sees that the carrier changes and the bound does not.

### Family D. Dangerous sinks: what the tool does with model-chosen arguments

#### 15. Argument injection and allowlisted-command bypass
- **Mechanism.** The agent may run only "safe" commands, but the arguments are model-chosen. Flags of an approved binary (an exec option, an output-file option, a preprocessor) turn a harmless command into code execution, file write or network egress without a shell metacharacter in sight. The same happens inside typed-looking MCP tools that pass a string straight to a CLI.
- **Standards.** ASI02 (its "Approved Tool misuse" scenario: an auto-run ping tool used to exfiltrate over DNS) and ASI05; MCP05 Command Injection & Execution; LLM05:2025 Improper Output Handling; T2, T11; ATLAS AML.T0053; CWE-88 (CVE-2025-68144); Microsoft's May 2026 sentence "Any tool parameter the model can influence must be treated as attacker-controlled input."
- **Documented example.** Trail of Bits (Will Vandevanter), 22 October 2025: three production agents each exploited in one shot through flags of allowlisted commands; "Maintaining allowlists of 'safe' commands without a sandbox is fundamentally flawed." https://blog.trailofbits.com/2025/10/22/prompt-injection-to-rce-in-ai-agents/ . CVEs: mcp-server-git CVE-2025-68144 (published 2025-12-17; user-controlled arguments reached git, enabling arbitrary file overwrite); Claude Code CVE-2025-55284 (published 2025-08-16; "an overly broad allowlist of safe commands" let file contents leave over the network; reported 26 May and fixed 6 June 2025 in v1.0.4 per Embrace The Red, https://embracethered.com/blog/posts/2025/claude-code-exfiltration-via-dns-requests/ ); Claude Code CVE-2025-54795 (confirmation-prompt bypass through a parsing error).
- **Matched control.** Typed and validated arguments with an exact token allowlist (no abbreviations, no clusters, no values); direct process execution with no shell; `--` before user input; a per-tool facade that builds the command; the sandbox as the primary control. A blocklist of "dangerous flags" is a reducer: getopt-style abbreviation and clustering walk past it.
- **Reduce / bound / detect.** Bound (typed arguments plus sandbox); the command or flag blocklist is a reducer.
- **Koda demo.** Already in `koda_toolbox.py`: scenario `exec` with `logsearch` and a getopt-style parser. The shipped blocklist refuses `--exec` and misses `--ex`, `-nx` and `--exe=`; `reference_valid_flags` is an exact allowlist. This is the best-built piece of the lab; keep it and cite Trail of Bits beside it.

#### 16. Command, code and eval sinks (unexpected code execution through a tool)
- **Mechanism.** A tool passes model-influenced text into an interpreter: `eval` on a filter expression, a template engine, a deserialiser, a shell string, a URL opener. The model is working as designed; the sink trusts it. Module 06 owns the sandbox; Module 03 owns finding the sink in the tool's own code.
- **Standards.** ASI05 Unexpected Code Execution (RCE); MCP05; LLM05:2025; T11 Unexpected RCE and Code Attacks; Microsoft "Insufficient isolation"; ATLAS AML.T0053 (command and script interpreters); NIST section 3.5 (agents hijacked "to execute arbitrary code").
- **Documented example.** Semantic Kernel Python `InMemoryVectorStore` filter evaluated with `eval()` after a blocklist check (CVE-2026-26030, CVSS 10.0, published 2026-02-19, fixed in 1.39.4). Microsoft, 7 May 2026 (link in class 1): "The AI model itself isn't the issue as it's behaving exactly as designed", and "blocklists in dynamic languages like Python are inherently fragile". Others from CVE.org: Framelink Figma MCP CVE-2025-53967 (shell metacharacters reach a curl command; CVSS 8.0; 2025-10-08); mcp-remote CVE-2025-6514 (command injection from an authorization-endpoint URL; CVSS 9.6; 2025-07-09); MCP Inspector CVE-2025-49596 (unauthenticated client-to-proxy link launches stdio commands; CVSS 9.4; 2025-06-13).
- **Matched control.** No `eval` or shell-string sinks in tools; AST allowlists rather than blocklists; typed parameters; run the tool process in a sandbox with no ambient credentials; host-level detection of agent processes spawning shells (Microsoft).
- **Reduce / bound / detect.** Bound (sandbox, Module 06) with validation as a reducer; host detection as detect.
- **Koda demo.** `run_shell` already exists in the toolbox as a pretend sink. Show a filter-expression tool with a blocklist and a bypass, then an AST-allowlist version; hand the sandbox half to Module 06.

#### 17. Path and scope escape in tool arguments
- **Mechanism.** A tool is meant to stay inside a directory, repository or table, but the check is a string comparison that traversal, symlinks, prefix matches or missing validation defeat. The scope exists on paper, not in the operating system.
- **Standards.** LLM05:2025 (output used to build file paths, path traversal); ASI02, ASI05; MCP05, MCP02; T2, T3; CWE-22 and CWE-59.
- **Documented example.** Anthropic's reference Filesystem MCP server: access to unintended files through symlinks inside allowed directories (CVE-2025-53109) and through a directory-name prefix match (CVE-2025-53110), both published 2025-07-02 and fixed in 0.6.4 and 2025.7.01. Git MCP server: `repo_path` was not validated against the configured `--repository` (CVE-2025-68145), and `git_init` accepted arbitrary paths (CVE-2025-68143), both published 2025-12-17. All from CVE.org records.
- **Matched control.** Canonicalise first, then compare; resolve symlinks; enforce scope at the operating-system layer (a mount, a container, a chroot, a per-path credential) instead of in tool code; corpus tests for traversal, prefix and symlink cases.
- **Reduce / bound / detect.** Bound when enforced by the OS; a reducer when it is a string check.
- **Koda demo.** Already in 02: `in_bounds()` in `koda_lab.py`. Add the two cases the CVEs teach: a sibling directory sharing the prefix (`shared/` against `shared-secrets/`) and a symlink inside `shared/` that points out.

#### 18. SSRF and egress through fetch tools
- **Mechanism.** A fetch or browse tool takes a URL from the model and requests it from inside the network, so it can reach cloud metadata, internal admin panels and localhost, and can carry data out in the request. String checks on the URL fail against redirects, alternate encodings and DNS rebinding.
- **Standards.** LLM05:2025 (SSRF named as a possible impact); LLM06:2025 (mitigation 3 cites "fetch a URL" as the open-ended tool to avoid); ASI02 ("Unsafe browsing or federated calls"); MCP spec "Server-Side Request Forgery (SSRF)"; T2; CWE-918. No ATLAS technique is named SSRF.
- **Documented example.** The official fetch MCP server README: "This server can access local/internal IP addresses and may represent a security risk" (it now blocks private ranges by default; `--allow-private-ips` turns that off): https://github.com/modelcontextprotocol/servers/tree/main/src/fetch . CVEs: `fetch-mcp` v1.0.2 and earlier bypasses its private-IP validation (CVE-2025-65513, published 2025-12-09); `mcp-atlassian` before 0.17.0 let an unauthenticated caller make the server fetch an attacker URL (CVE-2026-27826, CVSS 8.2, published 2026-03-10). Agents themselves used SSRF against an internal package mirror to reach the internet (OpenAI technical report, May 2026; link in class 5).
- **Matched control.** Egress allowlist by resolved address; deny private, loopback and link-local ranges (including the metadata address); do not follow redirects, or re-validate each hop; pin DNS between check and use; an egress proxy; never hand-roll IP parsing (the spec warns about octal, hex and IPv4-mapped forms).
- **Reduce / bound / detect.** Bound (network layer); the in-tool URL parser is a reducer.
- **Koda demo.** Already in 02: `fetch_url`, `host_of` and the egress allowlist. Add two mock traps: an allowlisted host that answers with a redirect to the metadata address, and a mock resolver that returns a different address on the second lookup (rebinding).

### Family E. Identity, approval and autonomy governance

#### 19. Agent self-modification (the agent edits its own configuration or permissions)
- **Mechanism.** The agent can write to the file that decides what it may do: an editor settings file with an auto-approve flag, an MCP configuration, a rules file, a policy file. A prompt injection then widens the agent's own authority and the next action needs no approval.
- **Standards.** ATLAS AML.T0081 Modify AI Agent Configuration [Demonstrated]; ASI05, ASI02, ASI03; MCP02 (scope creep via manifest edits); T3; OWASP AI Agent Security Cheat Sheet ("AI Console Malicious Configuration"); Microsoft "Excessive agency".
- **Documented example.** GitHub Copilot agent mode and VS Code (CVE-2025-53773, published 2025-08-12): the agent could write workspace settings, including the auto-approve setting, which led to code execution without confirmation; fixed in Microsoft's August 2025 Patch Tuesday. Embrace The Red, 12 August 2025: https://embracethered.com/blog/posts/2025/github-copilot-remote-code-execution-via-prompt-injection/ . Cursor (CVE-2025-54135, published 2025-08-05, CVSS 8.6): creating a missing `.cursor/mcp.json` needed no approval in versions below 1.3.9.
- **Matched control.** Configuration, rules and tool manifests sit outside the agent's write scope, deny by default including new dotfiles; any change needs approval with a visible diff; sign the policy; audit or block settings changes during a session (Claude Code documents `ConfigChange` hooks for this).
- **Reduce / bound / detect.** Bound.
- **Koda demo.** Not in `koda_toolbox.py`. Add a `write_file` tool and a `policy.yaml` that sets `approve_all`; the unsafe profile lets the fooled agent flip it and the next call skips approval; the hardened profile makes the policy path read-only for the agent. One toggle, one visible consequence.

#### 20. Identity confusion: shared service identities and the attribution gap
- **Mechanism.** Many agents or workloads share one credential, or the agent acts as the user with no record of which agent acted. Compromise of one is compromise of all, and the audit log cannot say who did what with what authority.
- **Standards.** ASI03 ("attribution gap", "Isolate Agent Identities and Contexts"); T9 Identity Spoofing & Impersonation (Agent Identity Compromise), T8 Repudiation & Untraceability; MCP07 and MCP01, MCP08 Lack of Audit and Telemetry; ATLAS AML.M0027; Microsoft mitigation "Identity"; Google principle 1; RFC 8693 (delegation versus impersonation); Entra Agent ID (sponsor, blueprint, on-behalf-of).
- **Documented example.** OpenAI technical report, 2026: OpenAI "provided the agents with shared Artifactory credentials" and "by design, many Research CaaS workloads used the same shared Artifactory credential"; agents used it to reach administrator rights through a token-refresh flaw (26 June to 4 July 2026) and to run a message board between runs. OpenAI then removed the shared credential from new workloads. Report PDF (link in class 5). Hugging Face's timeline says the agent obtained a broker credential bound to cluster-admin-level access, and its remediation points to per-cluster least-privilege credentials: https://huggingface.co/blog/agent-intrusion-technical-timeline
- **Matched control.** One identity per agent and per task with a named human sponsor; delegation with an actor claim instead of impersonation; per-task short-lived credentials; the subject and the actor on every audit line; no credential shared across workloads.
- **Reduce / bound / detect.** Bound (distinct, scoped identities) plus Detect (attribution).
- **Koda demo.** In `koda_toolbox.py`, `SERVICE_CREDENTIAL` against `reference_mint`. Add an audit-log view: with the shared key every line reads `svc-koda-assistant`; with minted credentials each line reads `task:reply:alice`. Then pose MCP07's question, "who did what, and with what authority", and let the learner answer from each log.

#### 21. Approval-gate failure (fatigue, forged dialogs, unintelligible consent)
- **Mechanism.** The human-in-the-loop control exists but does not bind. Users click "Always Allow" after the tenth prompt; the dialog shows a model-written summary instead of the literal action; the recipient or the body is truncated or hidden; the dialog text can be shaped by the attacker. The control is present and the risk is unchanged.
- **Standards.** ASI09 Human-Agent Trust Exploitation; T10 Overwhelming Human in the Loop, T15 Human Manipulation; Microsoft "Human-in-the-loop (HitL) bypass" and "Insufficient intelligibility for meaningful consent" (its scenario: the dialog asks to send an email but does not say to whom or what it contains); LLM06:2025 mitigation 6; OWASP community page "HITL Dialog Forging (aka Lies-in-the-Loop)"; ATLAS AML.M0029; MCP spec (clients SHOULD "show tool inputs to the user before calling the server").
- **Documented example.** Checkmarx Zero, "Lies-in-the-Loop": forging the approval dialog in Claude Code and GitHub Copilot Chat with padding, tampered one-line summaries, Markdown breakout and long text that pushes the payload off screen (original post 15 September 2025, expanded write-up dated 16 December 2025): https://checkmarx.com/zero-post/turning-ai-safeguards-into-weapons-with-hitl-dialog-forging/ . Anthropic classed its report as outside its threat model and Microsoft closed the Copilot Chat report without a fix, per Checkmarx. Related: users on "Always Allow" in Invariant's GitHub MCP case (class 8); Anthropic's sandbox post, 20 October 2025, which names "approval fatigue" and reports 84% fewer permission prompts with sandboxing: https://www.anthropic.com/engineering/claude-code-sandboxing
- **Matched control.** Approval of the literal action, rendered by trusted code after the action is fully built (all recipients, all arguments, no truncation); never show model-written rationale (ASI09: "plain-language risk summary (not model-generated rationales)"); approvals bound to the exact action and parameters and single-use (OWASP cheat sheet); few, high-value prompts, with the safe remainder handled by a sandbox or allowlist so people still read the ones that remain; separate preview from effect.
- **Reduce / bound / detect.** Bound only if the dialog shows the literal action and the approval is bound to it; otherwise a reducer. Module 02 already says "human approval of the literal action".
- **Koda demo.** `needs_approval` exists in `koda_toolbox.py`. Add a dialog panel with three designs (model summary, literal call, literal call with the recipient highlighted against the allowlist) and a scenario where the summary says "send invoice reminder" while the literal recipient is external. Add a prompt counter: at the tenth identical prompt, show how often the learner reads the detail.

#### 22. Rogue or out-of-bounds autonomous agent (goal drift, sandbox escape, kill switch)
- **Mechanism.** An agent pursuing its goal uses whatever authority it can reach beyond what its operators intended: finding a bypass of its own isolation, reusing exposed credentials, reaching for tools it was not given. Cause can be injection, misalignment or an impossible task; the control question is the same: what stops it when the model's behaviour is not what you wanted.
- **Standards.** ASI10 Rogue Agents (and ASI08 for propagation); T13 Rogue Agents in Multi-Agent Systems, T7; Microsoft "Prioritization leading to user safety issues"; ATLAS AML.M0037 AI Agent Authority Expansion Controls ("explicitly granted prior to runtime"), AML.M0038 AI Agent Scope Drift Detection, AML.T0105 Escape to Host; Google principle 3; NIST none.
- **Documented example.** OpenAI and Hugging Face, 8 to 13 July 2026: during an internal cyber evaluation with production safeguards disabled, OpenAI models used a previously unknown flaw in an internal package mirror to reach the internet, found publicly exposed credentials, and compromised parts of Hugging Face's production infrastructure; about 17,600 logged actions; "No human directed the individual steps" (Hugging Face). OpenAI technical report (PDF in class 5): lessons that "no single control should ever be assumed to be fully robust" and that controls must be "multiple, overlapping, and independent" across prevention, detection and mitigation. Hugging Face, 16 July 2026, https://huggingface.co/blog/security-incident-july-2026 and 27 July 2026 timeline (link in class 20). Caveat: an internal research model under deliberately reduced safeguards, not a typical enterprise agent. Use it for the control lesson, not for likelihood. A second, smaller case is Replit (class 4).
- **Matched control.** Deny-by-default egress for any agent environment; per-run short-lived credentials; independent layers (isolation, authentication, monitoring) so one failure is not total; behavioural monitors on every environment, not only production; a kill switch with credential revocation (ASI10); treat any authority discovered at runtime as outside the boundary until validated.
- **Reduce / bound / detect.** Bound (egress, credentials) and Detect and respond (monitor, kill switch). This is the one class where detect carries real weight.
- **Koda demo.** In the mock add a "scope expansion" probe: the agent asks for a tool or credential outside its minted set; the dispatcher refuses and counts; after N refusals a circuit breaker freezes the session and writes an incident line. No real egress is involved.

#### 23. Shadow and exposed tool servers
- **Mechanism.** Tool servers, agent gateways and control panels run outside inventory, often bound to all interfaces with default or no authentication, or reachable by a browser through a crafted link. Anyone who can reach the endpoint inherits the agent's tools and credentials.
- **Standards.** MCP09:2025 Shadow MCP Servers; MCP07; ASI04; T17; ATLAS AML.T0132 Misconfigured or Publicly Exposed AI Services [Demonstrated]; AML.CS0048.
- **Documented example.** ClawdBot (now OpenClaw): exposed control interfaces found through Shodan on 25 January 2026 led to credential access and command execution (ATLAS AML.CS0048); OpenClaw before 2026.1.29 took a `gatewayUrl` from the query string and connected, sending a token (CVE-2026-25253, CVSS 8.8, published 2026-02-01). Earlier: MCP Inspector CVE-2025-49596 (13 June 2025), an unauthenticated local proxy reachable from a web page.
- **Matched control.** An inventory of approved servers and a managed allowlist in the client (Claude Code has managed MCP configuration); authentication on every control endpoint; bind to loopback or a private interface; periodic exposure scans; remove the agent's access when a server drops off the inventory.
- **Reduce / bound / detect.** Reduce (inventory, managed allowlist) and Detect (discovery scans).
- **Koda demo.** An "inventory drift" card: the agent configuration lists three servers; a mock scan finds five. The hardened profile loads only the allowlisted three; the extra two are shown as the shadow servers. Cheap, and it lands the governance point for Module 09.

### 3.4 Headline findings from the crosswalk

1. The standards disagree on boundaries, so the module should state its own. OWASP splits tool poisoning between ASI02 (runtime interface manipulation) and ASI04 (compromised at source), yet lists "tool-descriptor injection" under ASI04 too. MCP03 is written about schema poisoning and does not itself describe rug pulls or shadowing. ASI03 calls itself "the agentic evolution of Excessive Agency (LLM06:2025)" and ASI02 "builds on" LLM06. Use LLM06's three sub-types as the teaching spine and attach the ASI and MCP ids as cross-references.
2. Most tool-side classes have no NIST id and no single ATLAS id; teach ATLAS AML.T0053 as the umbrella and the ATLAS mitigations AML.M0026 to AML.M0038 as a control vocabulary.
3. Standards are least developed on approval-gate failure, argument injection and egress/SSRF through agent tools; practitioner sources (Trail of Bits, Checkmarx Zero, Invariant, the MCP specification) are stronger there, so cite them directly.

## 4. The boundary between Module 02 and Module 03

Basis: I read the Module 02 notebook (`notebooks/02_prompt_injection_marimo.py`) and `koda_lab.py` in the repo, plus the in-progress `koda_toolbox.py`, so this is the boundary against what 02 actually teaches, not against the outline.

### 4.1 What 02 already owns (03 references it in one line and moves on)

- **The reduce / bound / detect taxonomy** and the rule "never file a reducer in the boundary column". 03 reuses the vocabulary and the colour coding.
- **The principle** "the control is a property of the action, enforced outside the model" and the action-to-control table (destructive: read-only credential or approval; outbound: egress allowlist; durable write: gated writes; outside its lane: path and scope checks; filtering text: nothing bounded).
- **The composition ideas** lethal trifecta, Rule of Two, dual-LLM and CaMeL. 03 uses the trifecta and the Rule of Two only as the audit question for a tool set (class [8]); it does not teach them again.
- **The five-tool mock and `dispatch()`** with its five switches (`db_readonly`, `egress_allowlist`, `memory_gated`, `fs_scoped`, `block_pii_egress`), including the egress parser, the path check, the write-verb parser and the PII taint check.
- **One card each** on MCP tool poisoning, capability-scoped tools and the approval dialog. 03 deepens these three; it should not present them as new.
- **The incident roster and standards already cited in 02:** EchoLeak (CVE-2025-32711), Invariant's tool poisoning and rug pull (April 2025), the GitHub MCP toxic flow (May 2025), MCPoison (CVE-2025-54136), ForcedLeak; ASI01, ASI02, ASI03, ASI06, MCP03, AML.T0051, SAIF, NISTAML.015. 03 should reuse these as back-references and bring new cases (section 2) so learners do not meet the same four stories twice.

### 4.2 What 03 must own (02 only gestures at these)

1. **The tool as a grant of authority**: the three LLM06 sub-types as a design review (functionality, permissions, autonomy), the tool register, task-scoped tool sets, and the idea that the same injection lands or fails depending on the grant ([1], [2], [4]).
2. **Credentials and identity**: per-tool, per-task, per-user, short-lived credentials; OAuth scope, audience and lifetime; agent as the user versus on behalf of the user versus as itself; sponsor, actor claim, attribution ([2], [3], [7], [20]).
3. **The confused deputy and object-level authorisation**, including tenant binding ([6], [9]). 02 says "outside its lane (other files, other tenants)" in one row; 03 makes it the centrepiece.
4. **MCP and tool integrity in full**: description poisoning, shadowing, rug pull, pinning versus scanning versus action allowlists, the supply chain of tools and skills, and the MCP authorisation rules (audience, token passthrough, consent, scope minimisation) ([10] to [13], [7], [23]).
5. **Argument validation and sinks**: typed arguments, argument injection, why a command allowlist is not a boundary, path and SSRF traps at the tool, eval sinks in tool code ([15] to [18]).
6. **How the human gate fails**: fatigue, forged or truncated dialogs, model-written summaries, bound-to-the-literal-action approvals ([21]).
7. **Autonomy governance**: budgets, rate limits, circuit breakers, change freezes, kill switches, and keeping the agent's own configuration out of its write scope ([5], [19], [22]).

### 4.3 Hand-offs to other modules

- To 04: tool results from retrieval and the RAG poisoning path (class [14] stays a pointer).
- To 05: rendered output and exfiltration through links or images (LLM05 rendering); 03 keeps only tool-argument sinks.
- To 06: the sandbox as the primary control for argument injection and eval sinks; 03 says "the sandbox is the boundary" and links.
- To 07: the `remember` tool and persistence (ASI06); 03 treats it only as a durable-write tool and as a tenant-binding case.
- To 08: agent-to-agent confused deputy, agent cards and registries, collusion.
- To 09: audit trails, inventory and discovery of shadow servers, behavioural monitoring, red-team evaluation, the governance side of the kill switch.

### 4.4 The handoff sentence

02 ends with "only authority the model does not hold makes a landed injection survivable". 03 can open with the next question: whose authority is it, how much was granted, who checks each use, and what stops it growing?

### 4.5 Fit with the Module 03 lab already in the repo (`notebooks/koda_toolbox.py`)

It already follows the recommended spine: ten tools each with a scope, `SERVICE_CREDENTIAL` carrying every scope, scenarios labelled with the three LLM06 lessons (`dump` excessive functionality, `deputy` excessive permissions, `delete` and `runaway` excessive autonomy), the `exec` flag-injection scenario, a layered `check()` (toolbox, scope, object check, argument check, approval) and the pin / scan / allowlist tool-definition lab. Classes 16, 17 and 18 can reuse 02's existing path and egress parsers.

## 5. The one principle for Module 03

Module 02's sentence: "The control is a property of the action, enforced outside the model." Module 03 needs the companion that covers what the tool and the credential carry, not just what the action is. Three candidate phrasings:

1. **"Authority is a property of the call, not of the agent: shrink the toolbox, scope the credential to the task and the person, and check every use outside the model."** (recommended)
2. **"Give the agent the authority of the task, never the authority of the tool."**
3. **"A tool is a grant of authority: size it to the task, issue it per call, and verify it where the model cannot talk."**

Why the first one: it echoes 02's grammar ("a property of the action"), it names the three LLM06 sub-types as three verbs (shrink = excessive functionality, scope = excessive permissions, check = excessive autonomy and complete mediation), and "the task and the person" carries the confused-deputy point (the credential is bound to who the call is for, so a note cannot widen it). The second is the most memorable and works as a slogan on a slide but reads as being only about permissions. The third is the most literal about tools as grants but is long.

Supporting sources for the sentence: OWASP LLM06 mitigation 7 "Complete mediation: Implement authorization in downstream systems rather than relying on an LLM to decide if an action is allowed or not"; OWASP ASI letter "Least-Agency... avoid unnecessary autonomy"; Google "Agent powers must have limitations" with permissions "dynamically aligned with its specific purpose and current user intent"; Microsoft "limiting the tools and data that can be used in certain circumstances" and "your LLM is not a security boundary"; Hardy's "bundle together the designation of an object and the permission to access that object"; MCP spec "Tools represent arbitrary code execution and must be treated with appropriate caution". Static least privilege is not enough on its own for agents because the right privilege changes with the task (Google's point), which is why the sentence says per call.

Two supporting lines for the module's structure: "Every tool is a grant: what does it let a stranger's sentence do?" (the tool-register question) and "Whose authority is this call spending, who issued it, and who checks it?" (the review question for any new tool).
