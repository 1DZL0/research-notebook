The one-line thesis

A compromised agent acts with the deployer’s authority, not the attacker’s. The attacker only needs standard user access. The blast radius is everything the agent was trusted to touch.

Framing decisions

  • The target: a company’s own containerised ops/dev assistant, running in Docker/Kubernetes (everyone has run a docker run). Container is both the agent’s home and the mitigation surface.
  • Structure: one deliberately vulnerable agent, ~150 lines of glue over an off-the-shelf SDK, with a config flag switching unsafe to hardened.
  • Two-passes: run the whole attack chain, then run the hardening / midigation fix

The rule: keep everything that can be shown, ship everything that has to be read.

The attack chain

1. Poisoned MCP tool. The company installs an MCP tool for a routine lookup; its return carries a hidden instruction the agent follows. Naive fix: “only allow vetted servers” but this one was vetted; the poison is in the data it returned, not the server. Real fix: tool-level authorization; treat all tool returns as untrusted.

2. Code execution. The injected instruction gets the agent to run code inside its container. Naive fix: “just run it in a container” you already are. Real fix: harden the sandbox: no socket, read-only FS, drop caps, non-root.

3. Container escape. The code breaks out to the host. Naive fix: “containers isolate by default” a mounted Docker socket is root on the host. Real fix: remove the socket mount; user namespaces; seccomp/AppArmor.

4. Reaches what it shouldn’t. On the host, the agent reads secrets / hits an internal service and the damage spreads. Naive fix: blocklist .. / allow known domains. Real fix: path canonicalisation; scoped network and credentials.

5. Hides and persists. The agent sends a reassuring “all done” and writes to its own memory, so tomorrow’s clean session is still compromised. Naive fix: “clear context each session.” Real fix: gate memory writes; sign/verify persisted state.

The visualisation

Not a diagram, an instrument panel over the running agent. It’s a dumb renderer tailing the agent’s trace log.

  • Two panels, side by side. Left = what the user sees (calm, helpful chat). Right = what actually happened (each tool call as a card: real arguments, real return). The lesson is the mismatch.
  • Colour the context by origin. Every block in the agent’s context gets a colour by source: system prompt / user / retrieved data / tool output. Show the agent obeying an instruction sitting in an untrusted-coloured block exactly as if it were trusted. This is the “the model can’t tell instructions from data” point, made visible.
  • Run both versions in lockstep. Same prompt, unsafe left, hardened right, stepping together. Identical for N steps, then one goes red with the reason and the other keeps going. Same agent, flag flipped → divergence point is unambiguous.
  • Blast radius as a map, not a list. Draw what the agent can reach as a shaded region over the company (host, containers, services, machines). Watch the attack walk, and stay inside the lit region. Least-privilege becomes spatial.
  • Put the damage somewhere other than the terminal. Exfiltrated data appears in a receiver window next to the agent; runaway resource use shows as a live counter ticking up. A log line lands as an abstraction; a reaction lands as a reaction.

The take-home pack

NoteWhat this is

The repo people take away from the session and the thing that makes the session reproducible without anyone presenting it. It’s the sandboxed emulator deliverable too: built once, shipped as both.

It’s a kit and a path. Grab the code if you know what you want, or follow the five stops in order and come out having done the whole thing yourself.

The idea

Everything is built around one vulnerable agent with a single flag: unsafe to hardened. You run the attack, watch it work, try the obvious fix, watch it fail, then flip the flag and watch the real fix hold. Security stops looking like a product you buy and starts looking like config you set.

The path

Five stops, mirroring the attack chain from the session. At each one: run it, break it, fix it, read the why.

1. Poisoned tool. Run the agent with the demo MCP tool. Watch it follow a hidden instruction from the tool’s return. Try “only allow vetted servers” — see it fail. Apply the real fix (treat tool returns as untrusted). Walkthrough: tool authorization.

2. Code execution. Trigger the agent to run code in its container. Try “just run it in a container” — you already are. Apply the sandbox hardening flags. Walkthrough: sandbox trade-offs and config.

3. Container escape. Watch the code break out to the host through a mounted socket. Swap compose.unsafe.yml for compose.hardened.yml and watch the escape die. Walkthrough: container isolation.

4. Reaching too far. See the agent read secrets / hit an internal service. Try blocklisting .. — watch it get around it. Apply scoped network and creds. Walkthrough: path canonicalisation, least privilege.

5. Persistence. Watch the agent write to its own memory so a clean session tomorrow is still compromised. Apply gated memory writes. Walkthrough: monitoring and persistence.

Then point the harness at your own agent and get a score.

What’s in the box

  1. The vulnerable agent — the exact one from stage, with the unsafe to hardened flag. Clone and run both.
  2. The trace renderer — point it at your own agent’s logs, not just the demo. The part worth more than the demos.
  3. The attack harness — point it at your own agent, get a score against the set of attacks. A harness gets re-run; a checklist gets read once.
  4. Written walkthroughs — the depth cut from the live session: sandbox comparison & config, path canonicalisation, monitoring signals, sensitive-data handling.
  5. Deployment checklist — the read-and-do artifact for a team shipping an agent.
  6. Conformity / ethics self-assessment — each attack tagged to its OWASP entry and AI Act article, so the same repo feeds T3.6 at near-zero extra cost.
